其一

工具、URL 与 HTTP

这一讲不急着讲漏洞。先让你从一个"只会打开网页的人"，变成能看清请求长什么样、 并且能把它改掉的人。Burp 和 HackBar 是这条路上的两把刀， URL 和 HTTP 报文是你接下来每次都要读的两样东西。

第一讲 · Burp 与 HackBar 完整流程 · 含 1 个靶场、3 个实操

这一讲在讲什么

Burp、URL、HTTP 头、Cookie、状态码 —— 这些词你大概都见过。 但第一次连起来看，往往不知道它们各自在说谁。这不怪你， 这些东西本来就是互相引着才成立的。

所以这里把它们重新排了个顺序，只围绕三个问题打转：

  1. 地址。你在浏览器里敲一串东西，它凭什么知道要去哪台机器、要哪个文件？—— 这是 URL。
  2. 页面。那台机器把一堆文字吐回来，怎么就变成你看到的网页了？—— 这是 HTML / CSS / JavaScript。
  3. 对话。这一来一回，机器之间究竟说了什么？—— 这是 HTTP 报文。

三个问题答完，剩下的都是练习：拿工具把这套东西拆开看，再看看拆开之后能改出什么花样。 改出花样那部分，就是"安全"。

安全的人看网页，和普通人看网页，眼睛落的地方不一样。

普通人看内容；我们看的是：这个内容由谁来、凭什么、按照什么规则送到你面前。

另外说明一下记号：带 「补充」 的，是讲台上没来得及展开、但迟早会撞上的部分； 带 「实操」 的，是自己电脑上就能跑一遍的。前者可以先跳过，后者建议都做。

先把家伙备齐

这一讲会用到的工具，真正要练熟的只有两个：Burp 和 HackBar。 另外几样装上备用，用到再折腾。

工具干什么用什么时候会碰到
BurpSuite抓包、改包、重放所有需要看清并改动请求的场合 —— 主力
HackBar在页面上改参数改 URL 参数、发 POST 数据，比开 Burp 快
phpstudy本地起 PHP 站想自己写个有洞的页面，然后打自己
WSL / VMware一台 Linux跑工具、跑靶场、装只有 Linux 才有的东西
Yakit流量分析、被动扫描Burp 之外换个视角看流量

下面两节把 Burp 和 HackBar 从头到尾走一遍：装好了界面哪块是干什么的、火狐怎么配、 怎么抓出第一个包、怎么改出一个不一样的结果。剩下三样放在最后简单交代。

装之前先说一句

别一上来装全套。先把 Burp 那条路走通 —— 能抓、能看、能改 —— 剩下的什么时候需要什么时候装。工具装了一堆却一个都不熟，是最常见的时间黑洞。

BurpSuite：从装上到改出第一个包

这是这一讲里唯一一个你会天天开的工具，值得花半小时摸熟。 下面按顺序走：它夹在中间干什么 → 界面哪块是干什么的 → 火狐怎么配 → 证书怎么装 → 怎么抓出第一个包 → 怎么改出一个不一样的结果。

它到底在干什么

平时是浏览器直接跟服务器说话。装了 Burp 之后，你在浏览器里设一个代理， 所有请求先交到 Burp 手上，再由它转给服务器。于是它夹在中间，能看、能停、能改。 专业点叫中间人代理（MITM Proxy）。

那 HTTPS 呢？HTTPS 本来是加密的，按说它看不见。但 Burp 会在你机器上装一张自己的 CA 根证书，浏览器信任了这张证书之后，Burp 就可以给每个网站现签一张证书， 解密 → 给你看 → 再加密送出去。

所以装不装那张证书，决定了你能不能抓 HTTPS。这一步几乎每个人第一次都会漏， 漏了之后的症状是：http 网站能抓，https 网站页面一片红，写着"您的连接不是私密连接"。

第一步：装，然后开起来

官网下 Community Edition（免费版），一路默认装完。开起来之后会问你两件事：

  1. 第一屏问项目放哪。选 Temporary project，点 Next。 （免费版本来就存不了项目，选它最省事。）
  2. 第二屏问用哪套配置。选 Use Burp defaults，点 Start Burp。

等几秒，主界面出来。左上角一排标签就是它的全部功能，别被吓到 —— 前期你只需要其中两个。

免费版少了什么

Community 版足够做完入门阶段的所有事。它缺的主要是：Intruder 跑得慢（限速）、 不能保存项目、没有自动扫描器。前两个影响不大，第三个到你有能力用它的时候再说。

第二步：界面认路

顶部那排标签，先认这几个：

标签中文干什么的

先只记 Proxy 和 Repeater 两个，其他的等你需要的时候自然会想起来。

第三步：让火狐的流量走 Burp

为什么用火狐？因为它的插件商店国内能直接打开，不用折腾网络。 而 Burp 自带的内嵌浏览器虽然更省事，但你以后会同时开很多窗口、要装别的插件， 还是自己的浏览器顺手。

  1. 火狐 → 右上角三横线 → 附加组件和主题 → 搜 FoxyProxy Standard → 添加到 Firefox。
  2. 装完工具栏会多一个小狐狸图标。点它 → Options（选项）。
  3. 在 Proxies 那一页点 Add（添加），按下面填：
    Title: Burp Proxy Type: HTTP IP address: 127.0.0.1 Port: 8080
    其他的都留空，点 Save。
  4. 再点小狐狸图标，在列表里选 Burp。图标变色（或者名字前面出现勾） 就表示这条路通了。
两个容易漏的
  • 火狐自己的代理设置（设置 → 网络设置）如果也配了一份，会和 FoxyProxy 抢。 装了 FoxyProxy 之后，以它为准就行，别两头都开。
  • 火狐默认可能开着 HTTP/3。它在 UDP 上跑，不走你的 http 代理， 表现为"明明请求了却抓不到"。地址栏输 about:config， 搜 network.http.http3.enable，双击改成 false。

第四步：装证书（不装就只能抓 http）

这一步是 HTTPS 的关键。顺序别乱：先让代理通，再去下证书。

  1. 保持 FoxyProxy 选着 Burp，在火狐里访问 http://burp。 这个地址不是真网站，是 Burp 自己接的。
  2. 页面右上角有一行 CA Certificate，点它，下载一个 cacert.der。
  3. 火狐 → 设置 → 隐私与安全 → 拉到最下面 证书 那块 → 点 查看证书。
  4. 切到 证书颁发机构 页签 → 导入 → 选中刚才那个 cacert.der。
  5. 弹出的框里勾上 「信任由此证书颁发机构来标识网站」，确定。
  6. 把火狐完全关掉再打开。

做完再访问一个 https 网站，页面正常显示、Burp 的 HTTP history 里能看到请求， 就说明成了。

第五步：抓出第一个包

现在开始真正的操作。全程只用鼠标，跟着点：

  1. Burp 开着，火狐的 FoxyProxy 选 Burp。
  2. Burp 顶部点 Proxy 标签。
  3. Proxy 下面有两个子页，点右边的 HTTP history（先别管 Intercept）。
  4. 切回火狐，访问 http://example.com。
  5. 回到 Burp，HTTP history 的表格里多了一行，Method 是 GET，URL 是 http://example.com/。
  6. 点这一行，界面下半部分会出现两块：Request 和 Response。
  7. 在 Request 那块的上方，能看到 Raw / Headers / Hex 三个切换。点 Raw。

这时候你看到的就是裸的 HTTP 报文，长这样：

GET / HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:128.0) Gecko/20100101 Firefox/128.0
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: zh-CN,zh;q=0.8
Connection: keep-alive
Upgrade-Insecure-Requests: 1

这就是第七节要逐行讲的那个东西。现在它不再是教材上的示意图，是你自己刚抓的。

HTTP history 里那几列
  • # 序号，只是顺序
  • Method GET / POST …
  • URL 请求到哪
  • Status 响应码，200 / 302 / 404 那些
  • Length 响应体多大
  • MIME type 响应是什么格式

表格上方有个输入框，可以按关键字过滤。找 login、admin、api 这几个词特别有用。

第六步：Repeater —— 改一个头，再发一遍

抓包只是看。真正干活是在 Repeater 里：把请求复制一份过来，改成你想要的样子， 点一下发一次，看服务端怎么反应。

  1. 在 HTTP history 里，右键你刚抓的那条请求 → Send to Repeater。（也可以先点中，按 Ctrl + R。）
  2. 顶部标签栏里的 Repeater 会闪一下，点进去。
  3. 左边是请求原文，光标点进去就能改，跟改文本文件一样。
  4. 右边是上一次的响应，空的也正常。
  5. 点左上角的 Send（或按 Ctrl + 空格）。
  6. 右边会刷出新响应，上方的状态码也跟着变。

这就是后面所有题的通用动作：抓一条 → 送 Repeater → 改 → Send → 看响应。 练熟这五下，一大半的题你都能开始动了。

实操

用靶场走一遍完整流程

  1. 先把靶场跑起来：
    python lab/zhulin_lab.py
  2. 火狐访问 http://127.0.0.1:8081/gate/2，页面显示"不让进"。
  3. Burp → Proxy → HTTP history，找到刚才那条 GET /gate/2， 点开看 Request 页签，注意这一行：Host: 127.0.0.1:8081。
  4. 右键 → Send to Repeater，切到 Repeater。
  5. 把 Host: 127.0.0.1:8081 改成 Host: admin.internal。
  6. 点 Send。右边的响应里出现 flag{...}。

你刚刚做的事，就是"改一个请求头"。听起来简单，但真实世界里 相当一部分漏洞，都是这样改出来的。

第七步：Intercept —— 把请求拦在门口

Repeater 是"事后改"。Intercept 是"当场拦"：请求发出去的一瞬间被 Burp 抓住， 你不动它，浏览器就一直转圈。

  1. Burp → Proxy → 子页切到 Intercept。
  2. 点一下 Intercept is off，它会变成 Intercept is on。
  3. 回火狐随便点个链接，页面卡住不动了。
  4. 回 Burp，报文就摆在那儿，可以直接改。
  5. 点 Forward 放它过去，或者点 Drop 扔掉。
最容易浪费半小时的一个坑

Intercept 开着忘了关，浏览器会一直白屏转圈，你会以为网断了、代理坏了、Burp 崩了。 记住它长什么样：Burp 里有个请求停着不动，等你点 Forward。

建议：平时把它关掉，只用 HTTP history 看历史。历史也不会丢，随时点开慢慢看， 比让浏览器干等着舒服得多。

几个早点养成的手感

  • Ctrl + R —— 送 Repeater。这是最高频的一个键。
  • Ctrl + F —— 在 HTTP history 里搜字。搜 password、token、api。
  • 右键 → Copy as curl —— 把一条请求变成命令行，方便复现和写脚本。
  • 右键 → Do intercept → Response to this request —— 连响应也拦下来改。做 XSS 题时常用。
  • Proxy → HTTP history 上方的过滤框 —— 只显示某个域名、某种状态码，把噪音滤掉。

抓不到包的时候，按这个顺序查

症状大概率是怎么办
HTTP history 一条都没有火狐没走代理点小狐狸图标，确认选中的是 Burp；Burp 得开着
https 页面一片红证书没装或没信任回第四步，重下 cacert.der，导入时勾上"信任"

HackBar：在页面上直接改参数

Burp 是站在门外的代理，HackBar 是坐在浏览器里的一把改锥。 点开它，当前页面的地址就摊在你面前，改参数、勾 POST data、点一次 Execute —— 页面重新加载。 它做不了 Burp 那么多事，但胜在快。

它和 Burp 的分工

你要做的事用哪个为什么
改一个 URL 参数，看回显变不变HackBar点两下就完事，不用开 Burp 翻历史
改 Cookie、Host、自己加一个头BurpHackBar 碰不到请求头
同一个请求改十几次对比结果Burp Repeater修改和结果并排摆着，不用来回切页面
看响应体的原始内容Burp页面渲染后的样子会丢信息
编码解码一串特殊字符都行HackBar 按钮直接点，Burp 有 Decoder

装

HackBar 是浏览器扩展商店里的东西，搜 HackBar 就能找到。 要注意的是：它这几年的版本比较乱，有的要填激活码，有的改名叫 HackBar V2， 不同版本界面略有出入。装的时候认准免费的那个，功能差别不大。

装完在工具栏会多一个图标，点一下，面板从页面上方或下方展开。 如果图标是灰的，先在浏览器里打开一个普通网页（about:blank 之类的特殊页面上它不工作）。

界面认路

面板不大，分三块：

  • 最上面一行按钮：Load URL 把当前地址读进来； Split URL 把 URL 和参数拆成两栏分别编辑；Execute 发出去。
  • 中间的输入框：你要发的东西写在这儿。 默认是 URL；勾上 Post data 之后，这里填的就是请求体。
  • 下面一片按钮：编码解码。 URL encode / URL decode、Base64、 Hex、MD5、SHA-1、ROT13 这些。 用法是选中输入框里的一段文字，再点对应按钮。
它到底做了什么

剥开看很简单：把地址栏改成你写的那串，然后刷新；或者构造一个 POST 请求发出去。 所以它只能碰 URL 和请求体，碰不到请求头 —— 请求头是浏览器的地盘， 页面里的脚本改不了。这也是为什么改 Cookie、改 Host 必须回 Burp。

一次完整的 GET 改造

实操

用靶场第四关练手

  1. 靶场跑起来（python lab/zhulin_lab.py），火狐打开：
    http://127.0.0.1:8081/download?file=notice.txt
    页面显示通知内容的全文。
  2. 点浏览器工具栏上的 HackBar 图标，面板展开。
  3. 点 Load URL，地址被填进输入框。
  4. 在输入框里把 file=notice.txt 改成 file=../flag.txt。
  5. 点 Execute。
  6. 页面重新加载，内容变成 flag{...}。

这和你在地址栏里手动改完按回车，效果是一样的。HackBar 的价值不在"能做新事情"， 在于把改参数、编码、发 POST 这几件事压缩到了一次点击。

一次 POST 提交

对正经网站做这件事之前，先在自己起的靶场或者明确授权的环境里练。 流程是：

  1. 打开目标页面（就是平时点提交按钮的那个页面）。
  2. 打开 HackBar，点 Load URL 读进地址。
  3. 勾上 Post data。这时候输入框的含义变了 —— 它代表请求体。
  4. 填上参数，格式和表单一样：
    username=admin&password=123456
  5. 点 Execute，页面返回的是服务端收到这组参数之后的响应。

这里能玩的花样就多了：把 role=user 改成 role=admin、 把 price=199 改成 price=1、把 id=1 改成 id=2。 这属于"参数篡改"，比改请求头更常见 —— 因为后端最容易忘的就是校验"你传上来的这个值该不该是你传的这个值"。

那几个编码按钮什么时候用

最常见的是 URL encode。前面第五节讲过，URL 里有些字符不能直接出现， &、=、#、空格这些都要转成 %XX。

另外一个是连点两次 encode。这对应"双重编码"： 服务端解一次码之后，%252e 变成 %2e， 如果只有第一道过滤器拦 ..，那它就被绕过去了。 遇到"明明按规则拦了却还能打进去"的题，先试试这个。

一句提醒

HackBar 改的是你自己浏览器发出的请求。也就是说 —— 你能改的东西，任何人也都能改。凡是客户端能改的，都不能拿来当权限依据。 这句在第七节讲 Cookie 的时候还会出现一次。

剩下三样，装上备用

这三样前两个月用得不多，但迟早会碰上。先说清楚各自解决什么问题，装法给链接，需要时再去弄。

phpstudy —— 在自己电脑上开个小站

一键装好 Apache/Nginx + PHP + MySQL，把 .php 和 .html 文件丢进它的 www 目录，浏览器访问 127.0.0.1 就能看到。

它的价值在于：你可以自己写一段有漏洞的代码，然后亲手打它。 网上抄来的题解看一百遍，不如自己写一个 echo $_GET['name']; 然后看着弹窗出现。

为什么能跑 php

因为 Apache 配了 mod_php（或转给 php-fpm）。浏览器请求 /a.php， Apache 发现后缀是 .php，就不当文本发出去，而是先交给 PHP 解释器执行， 把"执行完的输出"再发回浏览器。所以你在 .php 里写的代码，用户是看不到源码的； 但你在 .html 里写的东西，用户右键就能全看到。这个差别后面会反复用到。

VMware / WSL —— 一台可以随便弄坏的机器

装一个 Ubuntu。用途：跑工具、跑靶场、装各种只能装在 Linux 上的东西， 以及最重要的 —— 随便折腾，弄坏了删掉重来。

两个方案：

  • WSL：不用重启切系统，Windows 里开个窗口就是 Linux，文件互通。装法见 微软官方文档，一条 wsl --install 就差不多。
  • VMware：完整虚拟机，隔离更彻底，跑 Windows 靶机、做网络拓扑测试的时候必需。

Yakit —— 顺手再备一个

国产的，图形界面底下挂着一门叫 yak 的脚本语言。 和 Burp 是互补关系：Burp 强在手工改包和插件生态，Yakit 强在流量分析、被动扫描、批量 fuzz， 而且中文界面、开箱即用。官网在 yaklang.io， 安装包在 GitHub。

说句实在的

工具不是越多越好。前两个月，Burp + 一个干净的浏览器 + 一个能起本地站的 phpstudy 就足够你做完绝大部分 Web 入门题。装一堆却一个都不熟，不如把 Burp 的 Repeater 用出肌肉记忆。

看路：URL 拆成七段

它到底是什么

URL 的全称是 Uniform Resource Locator，翻过来就是"统一资源定位符"。 名字唬人，干的活很朴素：告诉别人去哪儿、找什么、带什么条件。

一个完整的 URL 最多能拆成七段。注意"最多" —— 大部分时候只用到三四段， 但真出事的时候，往往就出在那几段你从来没留意过的部分上。

分段英文它在说什么
协议scheme用什么规矩说话。http、https、ftp、file…
用户 / 口令user:pass有些服务把账号密码直接写在地址里
主机host域名或 IP，最终解析成一台机器
端口port这台机器上的哪一扇门。HTTP 默认 80，HTTPS 默认 443
路径path要哪个文件 / 走哪个接口
查询串query?key=value&key2=value2，额外的条件
片段fragment# 后面那段，只留在浏览器里，不发给服务器

端口是什么东西

有个比喻一直很好用：服务器是栋房子，端口是通向各个房间的门。

一台服务器只有一个 IP，但上面同时跑着网站、数据库、SSH。IP 只负责把包送到这栋房子， 具体进哪个房间，看端口号。所以看到 127.0.0.1:8080，意思是"本机这栋房子的 8080 号房间"。

几个要记住的：80 HTTP、443 HTTPS、22 SSH、 3306 MySQL、6379 Redis、8080 常见的备用 Web 端口。 端口范围是 1–65535，理论上随你用哪一个。

为什么安全的人记端口

因为默认端口会被防火墙放行，非默认端口常常是"内部服务忘了关"。 扫到一台机器开着 6379，那大概率是个没设密码的 Redis —— 这类事每年都在发生。

    补充一：URL 编码，绕过的老朋友

    URL 里能直接出现的字符是有规定的：空格不行，中文不行，&、=、?、# 这些有特殊含义的也不方便直接写。所以规矩是：把不方便的字符，换成 % 加两位十六进制数。

    几个例子：

    • 空格 → %20（表单里也常写成 +）
    • & → %26，= → %3D，# → %23
    • 中文「竹」→ UTF-8 是 E7 AB B9 → %E7%AB%B9
    • 点 . → %2E，斜杠 / → %2F

    为什么这对安全重要？因为「服务器看到的字符」和「过滤器检查的字符」经常不是同一串。 

    你可能想访问：   /download?file=../../etc/passwd
过滤器拦住 ..：  /download?file=..%2f..%2fetc%2fpasswd   ← %2F 解码后才是 /
再狠一点：      /download?file=%252e%252e%252f          ← 双重编码，解两次才现形

    这类差异有个统一的名字，叫 编码绕过。后面学注入、学上传、学 XSS，都会再见到它。 记住一句话就够：过滤和解码，谁先谁后，决定了洞在不在。

    补充二：同一个 URL，会被人看成两个

    看这串： 

    https://www.jiangnan.edu.cn@evil.com/login

    人的眼睛大概率扫到 jiangnan.edu.cn 就放心了。 但按规范，@ 之前那一段是 userinfo（用户名）， 真正的主机是 @ 后面的 evil.com。

    浏览器会把你送到 evil.com，同时把 www.jiangnan.edu.cn 当作"用户名"一起发过去。 钓鱼链接大量使用这个特性。所以看 URL 的正确姿势是：找到最后一个 @，它后面那一段才是真主机。

    类似的还有子域名伪装：jiangnan.edu.cn.evil.com 的主机是 evil.com，不是江南大学。 域名永远从右往左读。

    织骨：HTML / CSS / JavaScript

    这三样分工很清楚：

    • HTML —— 内容与结构。这里有个标题、那里有张图。
    • CSS —— 外观。标题多大、什么颜色、放哪儿。
    • JavaScript —— 行为。点了按钮会发生什么。

    MDN 上写得很全（中文入门）， 这里只挑和安全直接相关的那部分讲。

    HTML：一个页面最少要有什么

    下面这段几乎就是所有网页的骨架，逐行看：

    <!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>竹隐</title>
</head>
<body>
  <h1>我的第一个页面</h1>
  <p>Hello, Web.</p>
</body>
</html>
    标签作用
    <!doctype html>告诉浏览器"按现代标准解析我"。少了它，浏览器会切到怪异模式，布局全乱。现在它基本只剩这一个作用。
    <html>根元素，整个页面都包在里面。lang 属性标明语种，念屏软件、翻译靠它。
    <head>给浏览器和搜索引擎看的东西，不显示在页面上。
    <meta charset="utf-8">声明编码。不写就可能中文乱码。统一用 utf-8，别用别的。
    <meta name="viewport">让手机按手机屏幕的宽度渲染，不然整页缩成一小团。
    <title>标签页上那个标题，也是收藏时默认的名字。
    <body>用户真正看到的一切：文字、图片、按钮、表单。

    元素的基本形状是 <标签 属性="值">内容</标签>。 少数元素没有内容，比如 <img src="a.png">、<br>、<input>。

    补充：HTML 里三处最容易被翻出东西的地方

    一 · 表单的 name 属性

    <input name="username"> 里的 name，就是后端取值的 key。 你在页面上填 admin，发出去就是 username=admin。 所以做题时先看表单有几个字段、叫什么名字 —— 那基本就是后端的参数表。

    二 · 隐藏字段

    <input type="hidden" name="price" value="199"> 这种字段用户看不见， 但值明明白白躺在源码里，改一下再提交就是了。 凡是"价格、权限、用户 id、是否 VIP"这类东西靠隐藏字段传的，都是白给。

    三 · 注释

    <!-- 测试账号 admin / admin123 --> 这种注释，浏览器不显示， 但任何人右键「查看网页源代码」都能看见。CTF 里翻注释找到 flag 是老传统。

    CSS：能改的东西比你想的多

    写法有三种：外链 <link rel="stylesheet" href="a.css">、 页面内 <style>、元素上 style="..."。第三种优先级最高。

    核心就两个词：选择器（改谁）和属性（改成什么样）。 

    h1 { color: #1e2a23; font-size: 2rem; }   /* 所有 h1 */
.note { padding: 1rem; }                  /* class 叫 note 的 */
#header { position: sticky; }             /* id 是 header 的那一个 */

    CSS 在安全上出场不多，但有两个老东西值得知道： 点击劫持（把目标站点用透明 iframe 盖在你的按钮上，骗你点）和 CSS 注入（用户输入被直接拼进 style，能改页面元素甚至发出请求）。 先有个印象，遇到再说。

    JavaScript：浏览器里真正会"动"的东西

    它和 PHP、Python 一样是编程语言，只不过运行环境换成了浏览器。 最初只做页面特效，后来有了 Node.js，后端也能写。

    和后面最相关的四个东西：

    // 1. 找到页面上的元素
document.getElementById('out')

// 2. 改它的内容 —— 注意 innerHTML 会把字符串当 HTML 解析
el.innerHTML = '<b>' + 用户输入 + '</b>'   // ← XSS 的入口

// 3. 聊天 —— 发请求
fetch('/api/user?id=1').then(r => r.json()).then(console.log)

// 4. 读 cookie
document.cookie                             // ← 偷会话的第一站

    记住 innerHTML 那一行。凡是"用户输入"被当成 HTML 塞回页面， 就是 XSS 的经典长相。这一讲不展开，但你会很快在题里见到它。

    前端代码是公开的

    这是最重要的一条认知：发给浏览器的 JS、HTML、CSS，用户可以全部拿到、全部读懂、全部修改。

    所以前端做的任何"校验"都只是体验优化，不是安全边界。删除按钮置灰？ F12 改掉就是了。价格写死在前端？改一下就是了。真正的判断必须在后端做。

    反过来说，JS 文件对我们就是一座矿：里面可能有接口地址、隐藏的管理路径、 云服务的 key、注释掉的测试逻辑。右键查看源码、F12 翻 Sources、全局搜 api 和 admin， 是信息收集最便宜的第一步。

    传书：HTTP 报文

    前面两块是"货"和"包装"，这一块是"运"。浏览器和服务器之间真正传输的， 就是一段一段纯文本 —— 至少 HTTP/2 之前是这样。

    一次请求，四个动作

    1. 建立 TCP 连接。先握手，把路通上。
    2. 发一个 HTTP 报文。就是一段有固定格式的文本。
    3. 读服务端返回的报文。
    4. 关掉或者留着复用。HTTP/1.1 默认复用（Connection: keep-alive），省掉反复握手的开销。

    这四步在浏览器 F12 → 网络（Network） 里全能看见，不用装任何工具。 装 Burp 的好处只是：你可以在中途把它拦下来改。

    版本演进，知道个大概就行
    • HTTP/1.1：纯文本，一问一答，同一个连接上排队。可读性最好，抓包最容易学。
    • HTTP/2：二进制分帧，多路复用，头部压缩。人眼直接读不了，但 Burp 会帮你还原成 1.1 的样子。
    • HTTP/3：跑在 UDP 上（QUIC）。注意 —— 它会绕过你的 HTTP 代理，抓不到包的时候先想到这一条。

    请求报文：四段

    GET /item/list?page=2 HTTP/1.1          ← ① 请求行
Host: shop.example.com                   ← ② 请求头，一行一个
User-Agent: Mozilla/5.0
Accept: text/html
Cookie: PHPSESSID=298zf09hf012fh2
                                         ← ③ 一个空行，必须有
                                         ← ④ 请求体（GET 一般没有）

    请求行是三段：方法、路径、版本，中间用空格隔开。 注意路径里包含查询串 ?page=2，但不包含协议和主机名 —— 主机名在 Host 头里，这是 HTTP/1.1 的规矩。

    响应报文：也四段

    HTTP/1.1 200 OK                          ← ① 状态行
Date: Thu, 23 Oct 2026 02:14:06 GMT      ← ② 响应头
Server: Apache/2.4.39 (Win64) OpenSSL/1.1.1b
Content-Type: text/html; charset=utf-8
Content-Length: 1234
Set-Cookie: PHPSESSID=abc123; Path=/; HttpOnly
                                         ← ③ 空行
<!doctype html>...                       ← ④ 响应体

    状态行也是三段：版本、状态码、原因短语。 原因短语是给人看的，服务端爱写什么都行，真正的信息在数字里。

    状态码：先记这些

    数字名字它通常意味着
    200OK成了，东西在响应体里
    301永久重定向这个地址永久搬走了，去 Location 里那个
    302临时重定向临时跳一下，登录成功跳首页最常见
    304未修改你缓存里的还能用，我不重复发
    400请求错误你发的东西我看不懂，格式有问题
    401未认证你是谁？我没认出来
    403禁止我知道你是谁，但你不准进
    404不存在没这个资源
    405方法不允许地址对，但你不能用这个动作（如对只读接口发 POST）
    500服务器内部错误后端代码崩了
    502网关错误前面那层代理连不后面那层
    从做题角度看状态码
    • 301 / 302 里的 Location 是个跳转点。如果它接受你传进去的地址，就是任意跳转，能拿来钓 OAuth 的 token。
    • 401 和 403 的区别是"没认出来"和"认出来了但不让进"。有的站把 403 也当 404 返回，是为了不暴露资源存在 —— 这类差异本身就值得记一笔。
    • 500 的报错页面经常带堆栈、文件绝对路径、数据库语句。报错信息泄露是最便宜的洞。
    • 403 不等于安全。它只是这条路被挡了，换个路径、换个大写、加个 /、用 ..%2f，都可能绕过去。

    方法：动词决定语义

    方法语义用得着的地方
    GET取看页面、看列表、看详情。参数在 URL 里
    POST交登录、注册、下单、上传。参数在请求体里
    PUT改整体替换一个资源
    DELETE删删资源
    HEAD只要头不要体探活、看响应头
    OPTIONS问你支持啥探测允许的方法，常看 Allow 头

    两个术语，知道就行：安全方法（GET、HEAD，按约定不该改数据）和 幂等（同样的请求发一遍和发十遍，结果一样；GET、PUT、DELETE 是，POST 不是）。

    真实世界的偏差

    规范是规范，实现是实现。有的站用 GET 删数据（刷新一下就删一次）， 有的站只防了 GET 和 POST，PUT、DELETE 赤裸裸开着。 所以进一个站，先 OPTIONS 一下看 Allow 回了什么，比瞎猜省事。

    请求头 / 响应头：挑要紧的说

    MDN 上列了上百个头，实际做 Web 题，翻来覆去就是下面这十来个。 点开来看。

    Host这个请求要送到哪个站

    一台服务器上可能跑着几百个网站（虚拟主机）。它凭什么知道你要的是哪一个？就看 Host。 浏览器从 URL 里取主机名填进来，服务器拿它去匹配站点配置。

    为什么它能出事：TCP 连接早就建好了，Host 只是"到了之后报的门牌号"， 而这个门牌号是客户端随便写的。所以如果后端用它来拼绝对地址 —— 比如发送密码重置邮件时 点此重置：http://{$_SERVER['HTTP_HOST']}/reset?token=... —— 攻击者把自己的域名填进 Host，用户收到的链接就指向攻击者的服务器，token 直接送上门。

    这类问题叫 Host 头注入。相关的还有缓存投毒（CDN 按 Host 缓存，被污染的内容喂给所有人）。 防御很直接：用固定配置的域名，不要信任请求里的 Host。

    HTTP/1.1 规定这个头必须有，且只能有一个。缺了或者多了，规范上应该回 400 —— 但"规范上应该"和"实际怎么做"，往往是两回事。

    Origin我是从哪个站来的

    格式是 协议://主机[:端口]，比如 Origin: https://shop.example.com。 它只标明"来源"，不带路径，也不带查询串 —— 因为它关心的只是站点级的身份。

    这个头主要在跨域请求（CORS）里出现，普通请求一般没有。浏览器发 fetch 或 XMLHttpRequest 去另一个域名时，会自动加上它，服务端用它决定要不要回 Access-Control-Allow-Origin。

    做题视角：如果一个站的 CORS 配置成"把收到的 Origin 原样回给我，顺便允许带凭证"， 那就等于谁都能从自己的网页上读走用户的数据。看到 Access-Control-Allow-Origin: * 配上 Allow-Credentials: true，就要多看两眼。

    Referer我从哪个页面点过来的

    会带上来源页面的完整地址。用来做统计、防盗链、或者"只允许从本站跳转过来"。

    注意：请求头全都可以伪造，拿 Referer 做权限校验等于没有校验。 反过来，Referer 会把你当前页面的地址泄露给第三方 —— 如果那个地址里刚好带着 token 或口令，就漏了。

    （拼写确实是 Referer，当年定标准时拼错了，后来为了兼容将错就错。看到 Referrer-Policy 这个新头的时候别以为是两个东西。）

    Allow这个资源支持哪些方法

    响应头，在方法不被允许时（405）应该一并返回，告诉你"这里只收 GET, POST"。 Allow: 后面是空的，意思是"啥都不收"。

    做题视角：这是探测最省力的一个头。发一个 OPTIONS 过去， 回什么就说明后端开了什么，比一个个试快得多。

    Cookie我带着凭证来了

    浏览器自动带的。服务器之前用 Set-Cookie 种给它，之后每次请求到同一个域都会送回来。 

    Cookie: PHPSESSID=298zf09hf012fh2; csrftoken=u32t4o3tb3gg43; _gat=1

    一串 名字=值，用分号加空格隔开。

    核心认知：Cookie 就是你的身份本身。谁拿到那一串 PHPSESSID， 谁就是登录状态的你，服务器分不出来。所以后面所有关于 XSS、CSRF 的讨论，绕的都是这个东西。

    Set-Cookie服务器给你种一张凭证（重点）

    响应头。要种几个 cookie，就发几行 Set-Cookie。它后面挂着一串属性，每个都和安全有关：

    Set-Cookie: session=abc123; Domain=example.com; Path=/; Max-Age=3600; HttpOnly; Secure; SameSite=Lax

    Domain（可选，但很关键）

    指定这张 cookie 能送给哪些主机。设成 example.com，那么 www.example.com、mail.example.com、blog.example.com 全都能收到。不设的话，默认只给当前这个主机，不包括子域。

    所以：Domain 设得越宽，泄露面越大。主站和一堆子域共享同一张会话 cookie， 只要任何一个子域被拿下（或者子域上有个可以写 HTML 的地方），这张 cookie 就归人家了。 这叫「子域接管」式的会话劫持。

    HttpOnly

    加了它，JavaScript 的 document.cookie 就读不到这张 cookie 了。 这是专门用来防 XSS 偷 cookie 的。

    但别误会：HttpOnly 只是不让 JS 读，浏览器发请求的时候照样会带上它。 所以它挡不住 CSRF（CSRF 利用的正是"自动带上"这个特性），也挡不住 XSS 在页面里直接发请求。

    Secure

    只在 HTTPS 连接上发送。没这个属性，同网段的人抓个明文包就能拿到。

    SameSite（CSRF 的重点）

    控制这张 cookie 会不会跟着跨站请求一起发出去。三个值：

    • Strict —— 最严。只有从本站在页面上发起的请求才带它。 从外站点个链接过来，第一次请求不带 cookie，用户看到的是"未登录"状态，得再点一下。 体验差一点，最安全。
    • Lax —— 默认值（现在浏览器默认就是它）。跨站的 顶层导航（点链接跳过来）会带，但跨站加载图片、iframe、发起 fetch 都不带。
    • None —— 跨站也照带不误。设它的时候必须同时设 Secure， 否则浏览器直接拒绝这张 cookie。

    为什么这个属性是 CSRF 的关键：CSRF 的攻击方式就是"诱导你在已登录的状态下， 向目标站发一个不是你本意的请求"。如果目标站的会话 cookie 是 SameSite=None， 那么你在 evil.com 打开一个隐藏表单往银行站提交，浏览器会把银行的 cookie 一起带上 —— 银行看到的就是"你本人操作"。把它改成 Lax 或 Strict， 这条攻击链就断了一大半。

    X-Forwarded-For我的真实 IP 是……（谁能证明）

    请求经过代理、CDN、负载均衡之后，服务器看到的只有最后一跳的 IP。 为了把"真实客户端 IP"传下去，就加了这个头，格式是从左到右一路排下去： 

    X-Forwarded-For: 203.0.113.195, 2001:db8:85a3::8d3:1319, 150.172.238.178

    最左边是原始客户端，最右边是最近一跳的代理。

    问题在于：这个头是客户端可以自己写的。而且如果代理只是"在末尾追加"， 那攻击者随手填一个 127.0.0.1 在开头，后面跟着的可能是真的 IP —— 后端要是取最左边那个来判权限，就被骗了。

    所以：只信任它的服务端，等于把"我是谁"交给攻击者填。 后台白名单、限流、"仅内网可访问"这类判断，都可能是这个头的受害者。

    同类的还有 X-Real-IP、Forwarded、Client-IP、 X-Originating-IP、X-Remote-Addr —— 见到名字像"IP"的请求头， 先假设它可伪造。

    User-Agent我是什么浏览器（自述）

    客户端自报家门：浏览器、版本、操作系统。服务端常拿它判断设备类型、要不要给手机版。

    它同样可以随便改。有些站的"只有手机能访问"、后台爬虫识别、移动端专用接口， 都是靠 UA 判的 —— 改成 Mozilla/5.0 (iPhone; CPU iPhone OS ...) 就过去了。 这类题在 CTF 里很常见，判断依据就是这一条。

    Content-Type我发的是什么格式

    请求体和响应体的格式声明。最常见几种：

    • application/x-www-form-urlencoded —— 普通表单，长得像 a=1&b=2
    • multipart/form-data —— 带文件上传的表单
    • application/json —— 前后端分离的接口

    安全视角：后端经常按 Content-Type 决定用哪套解析逻辑。 把 JSON 接口的请求改成 application/x-www-form-urlencoded，可能走到另一个解析器上， 绕过某处校验 —— 这类"解析器不一致"是很多绕过的源头。

    Content-Length / Transfer-Encoding我这个包有多长（两个大哥）

    Content-Length 说"我的体有多少字节"； Transfer-Encoding: chunked 说"我的体是分块发的，不用给长度"。

    正常情况下这两个不会同时出现。如果同时出现，或者前后端对"该信哪一个"理解不一致， 就有一小段请求被"切"到下一次请求里 —— 这就是请求走私（HTTP Request Smuggling）， 能让攻击者劫持别人的请求。入门阶段知道有这回事即可，真遇到再深挖。

    Server / X-Powered-By我用的是什么（免费广告）

    前面那个例子里，Server: Apache/2.4.39 (Win64) OpenSSL/1.1.1b 把版本号、操作系统、SSL 库版本全写出来了。

    这叫 banner 泄露。对攻击者来说，这一步等于免费的指纹识别： 知道是 Apache 2.4.39，就去查这个版本的已知漏洞；知道是 PHP 7.x，就知道哪些函数的行为。

    防御方式是关掉或改成假信息。做信息收集时，第一个要看的就是响应头里的这一行。

    串起来看：一次典型的"改了就进"

    把上面这些拼起来，就是新人遇到的第一个真实场景：

    1. 你用普通账号登录，Burp 里看到响应里有 Set-Cookie: role=user。
    2. 你翻一个只有管理员能进的页面，返回 403。
    3. 你把请求里的 Cookie: role=user 改成 role=admin，重发。
    4. 返回 200，页面出来了。

    这说明后端直接信任了客户端送来的 role，而且它是明文存的。 这在专业上叫垂直越权；如果改的是 user_id=2 看上别人的订单，那叫水平越权。 名字不重要，记住这个模式：凡是客户端能改的东西，都不该被当作权限的依据。

    开炉：用 Docker 起一个靶场

    CTF 题目一般会给你一个 Dockerfile 或 docker-compose.yml， 几行命令就能在本机把出题人的环境原样跑起来。这一节讲怎么用。

    镜像和容器，一句话分清

    • 镜像（image） —— 一个打包好的、只读的系统快照，里面装着代码和依赖。相当于"光盘"。
    • 容器（container） —— 用镜像跑起来的一个实例，可读可写，跑完一删就干净。相当于"放进光驱播放"。

    同一个镜像可以开出十个容器，互不干扰。这就是它比"在本机直接装一遍"好的地方： 环境一致、不怕装坏、删掉不留痕。

    Dockerfile 长什么样

    FROM python:3.11          # 从哪个底包开始
WORKDIR /app              # 容器里的工作目录
COPY . .                  # 把当前目录的东西拷进去
RUN pip install flask     # 构建时执行一条命令
EXPOSE 5000               # 声明用哪个端口（只是声明）
CMD ["python", "app.py"]  # 启动时执行的命令
    指令干什么
    FROM基于哪个镜像开始。每条 Dockerfile 必须从这开始
    WORKDIR设定之后命令的工作目录，不存在会自动建
    COPY从宿主机把文件复制进镜像
    RUN构建时执行，结果被写进镜像
    EXPOSE声明容器内监听哪个端口（文档性质，不真的开端口）
    CMD启动时执行，一个 Dockerfile 只有一个

    两条命令跑起来

    # ① 构镜像：在当前目录找 Dockerfile，打上名字 ctf-web
docker build -t ctf-web .

# ② 起容器：把宿主机的 8080 接到容器的 5000
docker run -d -p 8080:5000 --name ctf ctf-web

    -p 8080:5000 是宿主机端口 : 容器端口，顺序别记反。 起来之后浏览器访问 http://127.0.0.1:8080 就是那台靶机。

    常用命令，抄下来就够

    docker images           # 本地有哪些镜像
docker ps -a            # 所有容器（含已停止的）
docker logs ctf         # 看容器输出，起不来先看这个
docker exec -it ctf sh  # 钻进容器里看文件
docker stop ctf         # 停
docker rm ctf           # 删（要先停）
docker rm -f ctf        # 停并删
docker rmi ctf-web      # 删镜像

    如果题目给的是 docker-compose.yml（多服务，比如 web + db），那更省事： 

    docker compose up -d --build   # 构建并后台启动
docker compose down            # 停掉并删干净
    Windows 上的两个坑
    • Docker Desktop 要先开 WSL2 或 Hyper-V，装之前先确认。装完重启一次。
    • 容器里跑的服务如果只听 127.0.0.1，宿主机映射端口也访问不到 —— 服务要监听 0.0.0.0。

    一句话总结这一节：看 Dockerfile 了解环境 → build 构镜像 → run 起容器 → 本地访问调试。

    演武：自己搭一个靶场，再亲手打一遍

    装 phpstudy 那一步，很多人装完就不知道拿它干什么了。这里给一个更好上手的东西： 一个只有两百行、只用 Python 标准库的靶场，不用装任何依赖， 不用 Docker，双击就能跑。

    实操

    起靶场（预计 2 分钟）

    1. 确认本机有 Python（3.8 以上都行）：
      python --version
    2. 在仓库根目录下，把靶场跑起来：
      python lab/zhulin_lab.py
      看到 靶场已开，去 http://127.0.0.1:8081 就成了。
    3. 浏览器开 http://127.0.0.1:8081，你会看到四道门。每道门背后一段 flag。
    4. 打不通的时候，先别急着换工具。回到 Burp 或 F12 里，把请求一个字一个字读完， 看看服务端到底在检查什么。

    四道门，四样毛病

    门它信了什么怎么过
    /gate/1 信了 X-Forwarded-For 加一个头 X-Forwarded-For: 127.0.0.1。浏览器里加不了，用 curl 或 Burp。
    /gate/2 信了 Host 把 Host 改成 admin.internal。域名随便写，反正没人真的解析它。
    /gate/3 信了 Cookie F12 → Application → Cookie，把 role 改成 admin；或者直接改请求头。
    /download 没做路径规范化 正常是 ?file=notice.txt。试试 ?file=../flag.txt。

    四道门依次对应你刚学的四样东西：XFF、Host、Cookie、路径。 打不过是正常的，卡住了就往下看代码 —— 墙是自己砌的，砖在哪儿一清二楚。

    工具：三样，从简到繁

    1. 浏览器 F12。Network 面板可以右键请求 → Copy → Copy as cURL，或者 Edge/Chrome 的「Edit and Resend」直接改头重发。够用。
    2. curl。命令行里改头最方便：
      curl -H "X-Forwarded-For: 127.0.0.1" http://127.0.0.1:8081/gate/1
    3. Burp。Proxy 里看到请求 → 右键 Send to Repeater → 改头 → Send。 这是以后天天要用的姿势。

    靶场的核心逻辑

    完整脚本在仓库的 lab/zhulin_lab.py，可以直接下载下来跑。这里贴最关键的两段：

    lab/zhulin_lab.py节选
    # 第一关：只看 X-Forwarded-For，而且只认第一个
xff = self.headers.get('X-Forwarded-For', '')
if xff.split(',')[0].strip() == '127.0.0.1':
    return self.reply(200, FLAG_1)
return self.reply(403, '只给本机看。')
    lab/zhulin_lab.py节选
    # 下载：把用户给的路径直接拼上来，没有做规范化
base = os.path.join(os.path.dirname(__file__), 'public')
target = os.path.join(base, name)          # name 完全来自 query
# 正常是 public/notice.txt，但 name 可以写成 ../flag.txt
with open(target, 'r', encoding='utf-8') as f:
    return self.reply(200, f.read())

    看懂这两段，你就懂了这类漏洞的通用形状：用户输入 + 直接信任 + 没有校验 = 洞。 后面所有的注入、穿越、越权，本质都是这一句话的不同变体。

    打完回头看

    这四关的修法，分别是：X-Forwarded-For 只从可信代理取、Host 用白名单、 权限状态存服务端会话而不是 cookie、路径先 realpath 再判断是否还在基目录内。 记住修法，比记住攻击方式有用。
